The app. This folder is the Expo project root (SDK 58, TypeScript, Expo Router): its config, its tooling and all of its code live here. Node and npm are all you need on the Mac; native builds run on EAS. Run every command below from `src/`.

## Commands

```sh
npm install          # or npm ci
npm test             # Vitest: **/*.test.ts in Node (the domain core, the library build, theme/contrast.test.ts, platform/db.test.ts, platform/store.test.ts and platform/suggestionBackfill.test.ts, and the Settings page's helpers in screens/settings/)
npm run typecheck    # tsc --noEmit
npm run lint         # ESLint: Expo rules, the core import rule, the no-literal-colours rule
APP_VARIANT=development npx expo start   # dev server; open it in the "Activity Reminder (dev)" app
npm run web          # web: currently does not bundle (see below)
```

`APP_VARIANT=development npx expo start` serves JavaScript to the **development** build (a dev client), not to Expo Go, so the dev app must be installed on the phone first. Set the variant: plain `npx expo start` (and `npm start`) resolves the `preview` config, so the dev-only Test mode stays hidden.

The web build no longer bundles since #21: expo-sqlite's web worker imports a `.wasm` file Metro isn't configured to resolve. The target is Android, so there are no web shims; `npx expo export --platform web` fails with `Unable to resolve "./wa-sqlite/wa-sqlite.wasm"`.

## The domain core

`reduce(state, event, deps)` is the only entry point. `CoreState` holds the settings (Active Hours per weekday, Interval, IANA time zone, `snoozeMinutes`: the Snooze delay, and the Suggestion settings: `exercisesPerSuggestion` 1–3, default 1; `bodyAreaMode` `'Weighted' | 'Random' | 'Strict'`, default `'Weighted'`; `difficulty`, the Difficulty ceiling, default `'Intermediate'`; `energetic` and `floor`, default `false`; `equipment`, the Equipment owned, default `[]`; `excluded`, the Excluded Exercise Ids, default `[]`; and `appearance` `'System' | 'Light' | 'Dark'`, the app's colour scheme, default `'System'`), the Reminders (fired ones plus the scheduled chain ahead, each with an Id deterministic from its fire time, a Suggestion snapshot of `{ id, name, dose, cue, bodyArea }` per Exercise, a status, and optionally `snoozes`, `refiresAt`, `done`, `fallback` (true: nothing matched the settings), `swappedOut` (the Ids swapped out, in Swap order) and `rotation` (on a Strict-built Reminder only, the `BODY_AREAS` index the next Strict Suggestion starts from)), `lastResponseAt`, `lastAppOpenAt` and `goalChanges` (Daily Goal changes `{ from: LocalDate, goal }`, oldest first).

Reminder statuses: `scheduled` (ahead, or fired with no final Response yet), `done` (with `done: [{ id, name, bodyArea }]`, the Exercises done in Suggestion order, copied from the Suggestion, not the library), `skipped`, `missed` (no Response before a later Reminder fired, or before its day's Active Hours ended) and `dropped` (snoozed, with its re-fire landing at or after its day's window end, so it never re-fires).

**Settling.** No JavaScript runs when a scheduled notification fires, so Missed and dropped can't be recorded at fire time. Every event first runs `settle(state, now)`, which derives them from the clock, comparing each Reminder's effective fire (`refiresAt ?? firesAt`): dropped at closing, Missed on replacement, Missed at closing. The window end is exclusive.

| Event | What it does |
|---|---|
| `AppOpened` | Records `lastAppOpenAt`. |
| `Rearm { timeZone? }` | JS is running: rebuilds the chain of upcoming Reminders over the next 7 days of Active Hours (no-Response fallbacks one Interval apart) and, when given, adopts the device time zone. Every Reminder not yet fired gets its Suggestion rebuilt under the current settings, in fire order, as if built when it fires (see **Suggestion rules**); fired Reminders stay as they are, Suggestion included. With nothing eligible and no fallback candidate either, nothing is scheduled. |
| `Response { reminderId, kind: 'Done', did }` | The guided flow's result, a final Response. Same guard as Skip. Keeps only the Ids in `did` that are in the Reminder's Suggestion, once each, in Suggestion order: with at least one the Reminder becomes `done` with their snapshots; with none (every card was Not this one) it is exactly a Skip. Either way `lastResponseAt` is now and the chain is rebuilt from now. |
| `Response { reminderId, kind: 'Skip' }` | A guarded Skip: accepted only for the outstanding Reminder (the latest fired one by effective fire, still `scheduled`, whether or not a Snooze re-fire is pending); the chain is rebuilt from the Skip time. A Done or Skip before a pending re-fire cancels it: `refiresAt` is cleared, `snoozes` kept, and the re-fire is not scheduled. A Reminder whose re-fire lands past closing stays outstanding until its day's window end. Anything else (duplicate, not fired, superseded, unknown, Missed, dropped) is a no-op that only dismisses the notification and returns the input state. |
| `Response { reminderId, kind: 'Snooze' }` | Not a final Response (`lastResponseAt` unchanged). Same guard, plus `canSnooze`: no re-fire pending and fewer than 2 Snoozes so far. Re-fires the **same** Reminder (same Id and Suggestion) at now + `snoozeMinutes` and counts the Snooze; the next fallback Reminder comes one Interval after the re-fire. The re-fire's notification says it was snoozed and, after the 2nd Snooze, offers only Start and Skip. A re-fire at or after window end is never scheduled; it settles as dropped. |
| `GuidedStarted { reminderId }` | The guided screen opened on this Reminder. Not a Response: `lastResponseAt` and `snoozes` stay. If it is the outstanding Reminder and its Snooze re-fire is pending, `refiresAt` is cleared and the chain is rebuilt without the re-fire; the chain then counts from the Reminder's own fire time (or `lastResponseAt`, if later), so the next fallback is the first grid time after now. The Reminder stays outstanding until the next one fires; leaving the guided screen doesn't bring the re-fire back. Anything else (not outstanding, no re-fire pending, unknown) returns the input state unchanged with no intents; no dismissal, the screen has already dismissed the notification. |
| `SetDailyGoal { goal }` | Records `{ from: tomorrow, goal }` (tomorrow in the Settings' time zone), replacing any change dated tomorrow or later, so today's goal never moves. A goal that isn't a whole number of at least 1 returns the input state. No intents. |
| `Swap { reminderId, exerciseId }` | Swap on the guided card. Not a Response. Settled first, it is accepted on the Reminders `guidedStart` opens (the outstanding one, or one of today's fired Reminders that settles as Missed or dropped), and only for an `exerciseId` in its Suggestion. The replacement (see **Suggestion rules**) takes its place, and the old Id is appended to `swappedOut`. `lastResponseAt`, `snoozes`, `refiresAt` and `rotation` stay; the chain ahead is rebuilt (only a `ScheduleChain` intent), so a pending Snooze re-fire carries the swapped Suggestion. With no candidate, or anything else, it returns the input state with no intents. |
| `Correct { reminderId, to: 'Done' \| 'Skip' \| 'Missed', did? }` | A correction from Today (or a late guided finish, see `guidedFinish` below), history only: accepted only for a Reminder of today (by its first fire) whose settled status is `done`, `skipped`, `missed` or `dropped` (so a fired Reminder superseded but not yet persisted, settling as Missed, can be corrected). To Done keeps the Ids in `did` that are in the Suggestion, as a Done Response does; with none left it is rejected, not turned into a Skip. To Skip or Missed removes the `done` list. Only the outcome changes: `lastResponseAt`, `snoozes`, `refiresAt` and the chain stay, and there are no intents. Anything else (a past day, the outstanding Reminder, not fired yet, unknown) returns the input state. |
| `ChangeSettings { change }` | A change on the Settings page (`core/settingsChange.ts`): `change` is any subset of the settings but `timeZone`. Validated first: Interval 15–120 in steps of 5; Snooze delay 5, 10, 15, 20 or 30; Exercises per Suggestion an integer 1–3; `bodyAreaMode`, `difficulty` and `appearance` in their enums; `equipment` a duplicate-free subset of `EQUIPMENT`; `excluded` strings; `energetic` and `floor` booleans; `activeHours` a complete record of the 7 weekdays, each `null` or an integer `{ start, end }` with `0 ≤ start < end ≤ 1440` (all days off is allowed). Any other key, `timeZone` included, makes it invalid. An invalid change returns the input state with no intents. Otherwise, settled, the change is merged into the settings and the chain is rebuilt (only a `ScheduleChain` intent, even for a Suggestion-only or Appearance-only change): the chain ahead runs from its anchor plus k × the Interval as if always set, and if that grid's next time is already past, the next Reminder is the first grid time after now (no catch-up fire). Fired Reminders keep their Suggestions, the outstanding one included; the next Snooze uses the new delay, and a re-fire already pending keeps its time. |
| `ResetSettings` | Reset settings to defaults. Settled, the settings become `defaultSettings` with the current `timeZone` kept, and the Daily Goal returns to `DEFAULT_DAILY_GOAL` from tomorrow by the `SetDailyGoal` rule; then the chain is rebuilt (only a `ScheduleChain` intent). The Activity Log is never touched: fired Reminders (the outstanding one too), `lastResponseAt`, `lastAppOpenAt` and past `goalChanges` stay. |

| Intent | Carried out by |
|---|---|
| `ScheduleChain { reminders }` | Replaces the whole scheduled chain: cancel every scheduled notification, schedule these (including any pending Snooze re-fire, whose entry has Start / Skip only after the 2nd Snooze). Each body is one `Name · Dose · Cue` line per Exercise; a fallback Reminder's body ends with the line `No Exercises match your settings`. |
| `DismissNotification { reminderId }` | Removes that Reminder's notification from the shade. |

Also exported: `guidedFinish(state, reminderId, did, now)`, what finishing the guided screen records (`core/guidedFinish.ts`, tested): on the outstanding Reminder, the `Response { kind: 'Done', did }`; otherwise, on the settled state (a replaced Reminder can still be stored as `scheduled`), null for an unknown Reminder, one not fired yet, or one from another day, and else a late answer as a correction of today's Reminder: with at least one Id of `did` in its Suggestion, `Correct { to: 'Done', did }` whatever its settled status (a finish with a Did it is a Done, even over a Skip); with none, null over `done` or `skipped` (no Did its never overwrites an answer) and `Correct { to: 'Skip' }` over Missed or dropped. The newer Reminder stays outstanding and the chain is untouched. `guidedStart(state, reminderId, now)` (same file, tested) is the Reminder the guided screen can open on: the outstanding one, or, on the settled state, one of today's fired Reminders that settled as Missed or dropped (e.g. just replaced by a newer one, or past closing), returned with that settled status; undefined for one already answered (done or skipped), from another day, not fired yet, or unknown. Also: `canSnooze(reminder, now)` (fewer than 2 Snoozes and no re-fire pending: the Snooze guard, and whether the guided screen shows Snooze), `outstandingReminder(state, now)` (the rule the Response guard uses; the adapter uses it to dismiss stale notifications), `isOutstanding(state, reminderId, now)` (whether that Reminder is the outstanding one, tested: the adapter uses it to accept a Done, Skip or Snooze, the guided screen to tell whether Snooze can show, and `guidedFinish` and `guidedStart` to recognise the outstanding Reminder), `todaysReminders(state, now)` (today's fired Reminders in the Settings' time zone, newest first) and `nextReminder(state, now)` (the earliest of the first scheduled Reminder after `now` and any pending Snooze re-fire), both for Today, `settle`, `effectiveFire` and `refireScheduled(reminder, settings, now)` (whether a snoozed Reminder is coming back: its re-fire is ahead and before its day's window end; so Today shows settled statuses and re-fire times, and a re-fire past closing as "Snoozed past closing" straight away), `isReminderId(id)` (tells Reminder notifications from others), `formatDose`, `exerciseGroups(library)` (`core/groups.ts`, tested: `{ floor, equipment }`, whether some Exercise has Position Floor and the Equipment some Exercise needs, in `EQUIPMENT` order; the Settings page shows the Floor toggle and an Equipment chip only for a group in it), `defaultSettings` (Mon–Fri 09:00–18:00, 45 min, 10-min Snooze, 1 Exercise per Suggestion, Weighted, Intermediate ceiling, no Energetic, no Floor, no Equipment, nothing Excluded, Appearance System) and `initialState`. The Settings page's allowed values, which `ChangeSettings` validates against (`core/settingsChange.ts`): `INTERVALS` (15–120 in steps of 5), `SNOOZE_DELAYS`, `BODY_AREA_MODES` and `APPEARANCE_SETTINGS`, and `WEEKDAYS` (Mon–Sun, the page's order); the enum lists are built with `allOf<T>()`, so one missing a member of its type, or holding one not in it, is a type error. `SettingsChange` (`core/types.ts`) is the `ChangeSettings` event's `change`, used by the validator and the handler's `changeSettings`. `addDays(date, n)` (`core/localTime.ts`) is the calendar date `n` days on.

**Suggestion rules** (`suggest.ts` and `swap.ts`, tested through `reduce`; all randomness from the injected `Random`).
- Eligible pool: Difficulty at or below the ceiling (Beginner < Intermediate < Expert), Energetic only when `energetic`, Position Floor only when `floor`, no Equipment or owned Equipment, minus `excluded`.
- Areas first. Weighted picks a Body Area among those with a candidate, at weight 3 if the Reminder's day (Settings' time zone) has no Done Exercise in it and 1 otherwise (coverage is the `done` lists of that day's `done` Reminders), then an Exercise uniformly within it. Random does the same with every area at weight 1. Strict takes the next N areas in `BODY_AREAS` order that have something in the pool, wrapping, from the `rotation` of the latest earlier Reminder that has one (else 0), and picks within each; it advances on every Suggestion, whatever the Response. Within a Suggestion each Exercise is from a different area while it can, and never twice.
- No-repeat window: the Exercises of the last 5 Suggestions, swapped-out ones included.
- Relaxation, in order: repeated areas (as many distinct as possible); the window shrinks one step at a time from 5 to 1, keeping the largest that gives the full count; fewer Exercises; in Strict, when its areas have nothing left even at window 1, the rest of the pool drawn as Random would (the rotation still advances); window 0 only when the whole pool was in the previous Suggestion.
- Fallback, only when the pool is empty: the base set (no Equipment, Position not Floor), ignoring Exclusions, the ceiling and Energetic, through the same rules with a count of 1 (the window, the mode and, in Strict, the rotation); the Reminder carries `fallback: true`.
- Swap's replacement, under the current settings, from the pool (the base set for a fallback Reminder): not in the window before this Reminder, this Suggestion or its `swappedOut`. Preference: the same Body Area, then an area not elsewhere in the Suggestion, then any; areas first at weight 1 within that. With nothing left the window shrinks step by step to 0, then swapped-out Exercises come back; never one already in the Suggestion.

**Days, Daily Goal and Streak** (`days.ts`, derived, never stored). A Reminder belongs to the local date (Settings' time zone) of its `firesAt`, its first fire; a Snooze re-fire doesn't move it.
- `dailyGoalFor(state, date)`: the last `goalChanges` entry with `from` on or before `date`, else `DEFAULT_DAILY_GOAL` (4).
- `isGoalDay(state, date)`: the day's `done` Reminders reach that day's goal.
- `dayTally(state, date)` / `todayTally(state, now)`: `{ done, skipped, missed, exercises }`, `exercises` being the total length of the day's `done` lists. Dropped and still-`scheduled` Reminders aren't counted.
- `streak(state, now)`: consecutive Goal Days backwards. Today counts if it is already a Goal Day; otherwise the count starts from yesterday, so an unfinished today doesn't break it. Days without Active Hours (by the current Settings' weekdays) are skipped, even one that reached its goal. The first earlier day with Active Hours that isn't a Goal Day ends it; it looks back no further than the earliest Reminder's day.
- `weekMarks(state, now)`: Mon–Fri of the current week (Monday to Sunday, so on a weekend the whole past Mon–Fri), one `DayMark` per day, by precedence `today` (even if already a Goal Day), `future`, `off` (no Active Hours), `goal`, else `missed`.

The chain is scheduled ahead because expo-notifications runs no JavaScript when a scheduled notification fires (see #21, "Owner decision: schedule the chain ahead"). Fired Reminders with no Response stay in the shade, bundled in one group, until JS next runs and dismisses the stale ones.

## Platform adapters

`platform/` follows the rules the background-responses probe proved on the Pixel (#12):

| File | What it does |
|---|---|
| `migrations.ts` | The schema, versioned by `PRAGMA user_version`, run once by `db()` right after opening (after `busy_timeout`). v0 → v1 creates the #21 schema if absent (a #21 DB is at version 0 with the tables already there); v1 → v2 (#22) adds `reminders.snoozes INTEGER NOT NULL DEFAULT 0` and `refires_at INTEGER NULL`, each only if missing; v2 → v3 (#23) adds `reminders.done_exercises TEXT NULL` (JSON), only if missing; v3 → v4 (#24) adds `reminders.fallback INTEGER NOT NULL DEFAULT 0`, `swapped_out TEXT NULL` (JSON) and `rotation INTEGER NULL`, each only if missing. Each step runs in one `BEGIN IMMEDIATE` transaction with its version bump and re-reads the version inside it, so a step is all or nothing and two JS contexts opening together can't apply it twice. Never drop or recreate a table; the file's header says how to add the next step. `store.test.ts` runs the v3 → v4 step on a v3 DB with history (in-memory `node:sqlite`, so Vitest needs Node 22.13 or later). |
| `db.ts` | One SQLite connection per JS context (`activity-reminder.db`; on Android `files/SQLite/activity-reminder.db`), `journal_mode = WAL`, `busy_timeout = 15000` (15 s: the chain, up to 100 notifications, is scheduled while `BEGIN IMMEDIATE` is held, and a cold-start headless Skip must outwait that rather than fail with `database is locked`). `write(fn)` serializes writes per JS context with a promise-chain mutex and runs each as `BEGIN IMMEDIATE … COMMIT`, `ROLLBACK` on error. **Never `withExclusiveTransactionAsync`**: it opens a second connection without `busy_timeout` and lost Skips to `database is locked` on the Pixel. |
| `store.ts` | `CoreState` in tables `reminders (id, fires_at, suggestion, status, snoozes, refires_at, done_exercises, fallback, swapped_out, rotation)` and `meta` (`settings` JSON, read over `defaultSettings` so settings stored before a field existed, e.g. #21's without `snoozeMinutes`, get its default; `last_response_at`, `last_app_open_at`; `goal_changes`, the Daily Goal changes as JSON, absent (a DB from before #25) read as none, so the default goal). `snoozes` 0 ↔ absent, `refires_at` NULL ↔ absent, `done_exercises` (a JSON array of `{ id, name, bodyArea }`) NULL ↔ absent `done`, `fallback` 0 ↔ absent and 1 ↔ `true`, `swapped_out` (a JSON array of Exercise Ids) NULL ↔ absent `swappedOut`, `rotation` NULL ↔ absent. `loadState` fills a Suggestion snapshot's missing `bodyArea` (stored before #23) from the library by Id (`suggestionBackfill.ts`, tested); an Exercise no longer in the library keeps its snapshot as it is. `saveState` replaces future Reminders and upserts fired ones, including their settled status (Missed, dropped) and a Swap's new Suggestion and `swappedOut`, in multi-row INSERTs of 90 rows (10 parameters each, under SQLite's 999 limit). The mapping, the batching and the v4 migration are tested in `store.test.ts`, against an in-memory `node:sqlite` behind the slice of expo-sqlite's API the store uses. The guarded updates match the core's guard and are accepted only when exactly one row changed. Done and Skip share `id=? AND status='scheduled' AND fires_at<=?` (a pending re-fire doesn't block them) and clear a re-fire still ahead with `refires_at = CASE WHEN refires_at > ? THEN NULL ELSE refires_at END` (`snoozes` kept): `guardedSkip` sets `status='skipped'`, `guardedDone` sets `status='done', done_exercises=?`. `guardedSnooze` is `UPDATE reminders SET snoozes=snoozes+1, refires_at=? WHERE id=? AND status='scheduled' AND fires_at<=? AND (refires_at IS NULL OR refires_at<=?) AND snoozes<2`. `responses (reminder_id, kind, source, at)` gets a row only when that update wins: kind `Done`, `Skip` or `Snooze` (a Done with nothing done is logged as the Skip it is), source `bg-task`, `fg-listener` or `app`. A late guided finish saved as a correction (`finishGuided`) is logged too, kind `Done` or `Skip`, source `guided-late` (the column is TEXT: no migration). |
| `notifications.ts` | `setup()`: permission, the high-importance `reminders` channel, two categories, `reminder` (Start, Snooze, Skip) and `reminder-no-snooze` (Start, Skip), where Start opens the app and the others don't, and the foreground handler. `scheduleChains`: `ScheduleChain` cancels **scheduled** notifications only (presented ones stay) and schedules each Reminder with a `DATE` trigger, identifier = Reminder Id (a Snooze re-fire keeps it), the title from the intent, the category from the entry's `actions` (no `snooze` → `reminder-no-snooze`), `data: { reminderId }`, one Android group (`threadIdentifier`); at most 100 at once, one after another. `handler.ts` calls it **inside** the `write()` transaction, after the state is saved and before COMMIT, so the last chain committed is the last chain armed; a throw rolls the transaction back. `dismissNotifications` (`DismissNotification`) runs after the commit. `dismissStale` removes every presented Reminder except the outstanding one. `opensGuided(actionId)` is true for Start and a body tap (`DEFAULT_ACTION_IDENTIFIER`); `dismissReminder(id)` removes one notification (`respond`, first; the guided screen, on mount). |
| `handler.ts` | `respond(event, source)` is the one guarded path for every Response, from the shade or the app: dismiss the notification first, then in one `write()` load the state, accept only if `isOutstanding(state, reminderId, now)` (checked before `reduce`), `reduce` the Response (a reduce that returns its input state, e.g. a third Snooze, is a no-op), run the guarded update for what the core made of it (`guardedDone` with the core's `done`, `guardedSkip` also for a Done with nothing done, or `guardedSnooze`), log the Response, save the settled state and schedule the chain; after the commit, apply the dismissals. It returns whether the Response was accepted. `handleAction(actionId, payload, source)` is what both notification delivery paths call: Skip and Snooze go to `respond`; Start and a body tap record nothing (the foreground side opens the guided screen). When the app is alive in the background both paths fire in one JS context and the guard makes the second a no-op. The guided screen calls `respond` with source `app` for its Snooze; its Skip (`finishGuided` with no Ids) and its finish go through `finishGuided`. `finishGuided(reminderId, did)` reads the state and asks the core's `guidedFinish`: null logs "nothing to record" and returns false; a Done Response goes to `respond(…, 'app')`, and if that isn't accepted (a newer Reminder fired or a shade answer landed between the read and the lock) it falls through to the late path once; a `Correct` goes to the late path. The late path, in one `write()`: load, recompute `guidedFinish` with a fresh `now`, and only if that is a `Correct` the core accepts (a new state), save it, and log a `responses` row (`Done` or `Skip`, source `guided-late`) only if the Reminder's settled status changed (a second Done on a done Reminder may change its Did it list but logs nothing); after the commit, notify. No intents, so nothing is scheduled. It returns whether something was recorded. `startGuided(reminderId)` runs `GuidedStarted` in one `write()`: load, `reduce`, and only if the core changed the state, save it, schedule the chain inside the lock and notify; it returns the resulting state and the `now` it was computed at, which the guided screen passes to `guidedStart`. The guided screen calls it once on open. `swap(reminderId, exerciseId)` runs `Swap` (the guided card's Swap) in one `write()`: load, `reduce`, and only if the core changed the state, save it, schedule the chain inside the lock and notify after the commit; it returns the swapped Reminder, or null for a no-op (no replacement, or the Reminder no longer accepts a Swap). A Swap isn't a Response: no `responses` row. `correct(reminderId, to, did?)` runs `Correct` (Today's correction sheet) in one `write()`: load, `reduce`, and only if the core accepted it (a new state), save it and notify. A correction has no intents, so nothing is scheduled, and no `responses` row is written. It returns whether it was accepted. The Settings page's three calls share one path: `changeSettings(change)` (`ChangeSettings`), `resetSettings()` (`ResetSettings`) and `setDailyGoal(goal)` (`SetDailyGoal`) each run in one `write()`: load, `reduce`, and only if the core accepted it (a new state), save it and schedule the chain inside the lock, then notify after the commit. `SetDailyGoal` has no intents, so it schedules nothing. They aren't Responses: no `responses` row. Each returns whether it was accepted; a rejected change (the core's validation) writes nothing. `rearmOnOpen()` runs `AppOpened` + `Rearm` (device time zone) the same way. Only adapters touch `Date.now` and `Math.random`. |
| `task.ts` | The background notification task (`TaskManager.defineTask` at module scope, `Notifications.registerTaskAsync`), loaded from `index.ts`. It reads the Reminder Id from `content.dataString` (a JSON string, what the task gets on the Pixel), falling back to `content.data`, and calls `handleAction` (so Start is nothing to record there). |
| `useReminderRuntime.ts` | Mounted by the root layout: `setup()`, `rearmOnOpen()` on launch and whenever `AppState` becomes `active`, and the foreground response listener (`handleAction`, source `fg-listener`). Start and a body tap open `/guided/[reminderId]` with `openGuided(reminderId)` (also used by Start on Today): from the listener, and on a cold start (the app launched by the tap) from `getLastNotificationResponse()`. Each response is routed once per JS context (keyed by notification, date and action) and then `clearLastNotificationResponse()`, so a later launch doesn't reopen it. Start has `opensAppToForeground: true`, so on a locked phone Android asks to unlock first. |
| `useAppearance.ts` | Mounted by the root layout: reads the stored `settings.appearance` on launch and after every write in this JS context (`onStateChanged`), and when it differs from the last one applied calls `Appearance.setColorScheme`: `'auto'` for System (never the deprecated `'unspecified'`), `'light'` or `'dark'`. On Android that sets AppCompat's night mode; the activity's configuration change emits `appearanceChanged`, so `useColorScheme()`, and with it the theme's `useScheme()`, `useColors()`, the navigation theme and the status bar, follow without anything else. The override isn't persisted by Android, so a cold start shows the system scheme until the stored state is read. |
| `notificationPermission.ts` | For the Settings page: `useNotificationsOn()`, whether notifications are allowed (`getPermissionsAsync().granted`), read on mount and whenever `AppState` becomes `active`; `openSystemSettings()` (`Linking.openSettings()`), its Turn on. |
| `useCoreState.ts`, `variant.ts` | Read-only helpers for screens: the stored state (re-read after each write in this JS context, once just after the next Reminder is due: a one-shot `setTimeout` to `effectiveFire(nextReminder(state, now))` + 500 ms, re-armed on every new snapshot and cleared on unmount, and once a minute as a backstop) and the app variant from `extra.appVariant`. |

### Today

- **Hero** (`screens/today/Hero.tsx`, on `accent.hero`): the date, the Streak (`streak`), one Daily Goal dot per goal (`dailyGoalFor` of today in the Settings' time zone), filled for each Done (`todayTally`), with "N of G today", and the status line: "Next Reminder HH:MM" from `nextReminder` (with the weekday when it isn't today, and "(snoozed)" for a Snooze re-fire), or "No Reminders scheduled". Pause and Day Off join it in #26. While Today is in front the status bar icons take `text.onHero`'s tone.
- **Tiles** (`Tiles.tsx`): History · Achievements · Settings, each `router.push`ed on the root Stack, so the page's back arrow and Android back return to Today. No "new" dot until #28.
- **Tally and Reminders** (`ReminderList.tsx`): "N done · N skipped · N missed · N Exercises" (`todayTally`), then `todaysReminders` newest first: time, a dot in the status's colour (the outcome colour for done, skipped and Missed), the Suggestion, the status (Done with its Exercises, Skipped, Missed, "Snoozed, back at HH:MM", "Snoozed past closing" for a dropped one or one whose re-fire lands past closing, "Waiting for you") and a "snoozed ×N" tag. - **Correction sheet** (`CorrectionSheet.tsx`, React Native's `Modal`): Done / Skip / Missed, the current outcome preselected (none for a dropped one); for Done, a checklist of the Suggestion's Exercises, pre-checked from its `done` list, and Save disabled while none is checked. - **Week panel** (`WeekPanel.tsx`): Mon–Fri from `weekMarks`: `goal` filled `day.goalDay`, `missed` filled `outcome.missed`, `off` filled `line.divider`, `today` ringed in `accent.hero`, `future` outlined; a Goal Day / Missed goal legend. Tapping it opens History.

### The guided screen

`app/guided/[reminderId].tsx`, opened by Start or a body tap on the notification, or Start on Today. On mount it dismisses the Reminder's notification, then calls `startGuided` once, which cancels a pending Snooze re-fire (`GuidedStarted`) so the re-fire can't arrive mid-flow; on the state it returns, it asks `guidedStart`: the outstanding Reminder opens, and so does one of today's that settled as Missed or dropped, so Start on a Today that hasn't redrawn yet (a newer Reminder fired a moment ago) never dead-ends. It shows the fallback when `guidedStart` refuses it (already answered, another day, unknown), when its Suggestion is empty, or when a Snooze isn't accepted: "This Reminder isn't waiting any more", "It was already answered, or it isn't one of today's. You can change today's answers on Today." and a link back to Today. Otherwise it keeps that Reminder for the whole session, even if it stops being outstanding, and it shows one card per Exercise of the Suggestion: Body Area, Name, the Dose large (`formatDose`), the Cue, the start and end photos (looked up by Id in `exercises`, then `photoSource`; none if missing), "N of M", and **Swap** / **Not this one** / **Did it ✓**. **Swap** calls the handler's `swap` for the card's Exercise: the card then shows the new Exercise (Body Area, Name, Dose, Cue, photos, the timer reset) at the same position and the same "N of M", the cards already answered keep their marks, and a later Did it records the swapped-in Id. A no-op keeps the card and shows "Nothing else fits your settings" under Swap until the next Swap or answer. While a Swap is in flight Swap and the answers are disabled (a ref guards the same tick), so a double tap can't swap twice. A Swap isn't an answer, so the break links stay as they were. A fallback Reminder (`fallback: true`) shows a banner above the card for the whole flow, Swaps included: "No Exercises match your settings" and a **Settings** link that pushes `/settings`. A seconds Dose gets **Start timer**, a countdown that can be restarted (for an each-side Dose, once per side). Until the first card is answered, the break links are **Snooze**, shown only while `isOutstanding` on the latest snapshot says this Reminder is outstanding and `canSnooze` allows it (fewer than 2 Snoozes and no re-fire pending; after the cancel on open, so a once-snoozed Reminder can be snoozed a second time), which goes through `respond(…, 'app')` and then back to Today, or shows the fallback if it turns out a no-op (the Reminder ended meanwhile); and **Skip**, always, which calls `finishGuided` with no Ids and goes back to Today: on the outstanding Reminder that is a Skip, on a Missed or dropped one a correction to Skip. From the second card on, **End here** takes their place. The last card's answer and End here both call `finishGuided` with the Ids marked Did it so far and then go back to Today, recorded or not (what records nothing has nothing new to record): on the outstanding Reminder that is the Done (the core turns an empty list into a Skip); if a newer Reminder fired or it was answered from the shade meanwhile, a finish with a Did it is saved as a correction (see `guidedFinish`), so it isn't lost. Back (the ‹ Today link, Android back or the back gesture, through `usePreventRemove`) before any card is answered records nothing and doesn't bring a cancelled re-fire back: the Reminder stays outstanding until the next Reminder replaces it. Once a card is answered, back saves exactly like End here (`finishGuided` with the Ids marked Did it so far) and then goes to Today; a ref tracks the finish, so back during a finish doesn't finish twice and the finish's own navigation to Today is let through. No celebration until #28.

### Settings

`app/settings.tsx`, pushed from Today's Settings tile (the back arrow, Android back and the back gesture return to Today), with its parts in `screens/settings/`. One scrolling page from the stored state, every row showing its current value, in #15's order:

- **Schedule.** **Active Hours** (`ActiveHoursRows.tsx`): day chips Mon–Sun; **Main hours**, one window for the enabled days; and one row per enabled day showing "Main hours" or its own window (an override). The record ↔ main window + overrides mapping is `activeHours.ts` (pure, tested): the main window is the most common window among the enabled days, a tie going to the earliest weekday; a day turned on gets the main window (09:00–18:00 when every day was off); changing Main hours moves every day on it and leaves the overrides; a day's sheet sets its own window or, for an override, **Use main hours**. Windows are picked in a sheet with a Start and an End list in 15-minute steps (`WindowSheet.tsx`), the End always after the Start. **Interval**: 15–120 min in 5-min steps. **Snooze delay**: 5 / 10 / 15 / 20 / 30 min.
- **Daily Goal**: 1–12, set through `setDailyGoal`. The row shows today's goal (`dailyGoalFor` today in the Settings' time zone) and, when a different goal starts tomorrow, "N from tomorrow" (`dailyGoal.ts`, tested). The picker is titled "Daily Goal from tomorrow" and preselects tomorrow's goal.
- **Suggestions**: Exercises per Suggestion 1 / 2 / 3, and Body Area mode, Weighted / Random / Strict rotation, each with a one-line hint.
- **What I can do**: Difficulty ceiling (Beginner / Intermediate / Expert), the Energetic switch, the Floor switch only while `exerciseGroups(exercises).floor` is true, and an Equipment chip only for each item in `exerciseGroups(exercises).equipment` (with none, the row says "No Equipment Exercises yet"). The owned list is saved in `EQUIPMENT` order.
- **Exercise Library**: a disabled placeholder row, "Browse and exclude Exercises: coming soon", until #30.
- **App**: Notifications On or Off (`useNotificationsOn`, rechecked when the app comes to the front), with **Turn on** while Off, which opens the app's system settings; Appearance System / Light / Dark (applied by `useAppearance`); **Reset settings to defaults**, behind a confirm (Cancel / Reset) that says the Activity Log is kept, then `resetSettings`; the version (`expoConfig.version`, plus the variant in the development build).

Pickers are JS only: a sheet on React Native's `Modal` with a list (`PickerSheet.tsx`, `WindowSheet.tsx`, on `Sheet.tsx`), chips or switches; no native picker. Every change goes through the handler (`changeSettings`, `setDailyGoal`, `resetSettings`); the page shows only what is stored, so a change the core rejects leaves the row as it was. One change at a time: the controls are disabled while one is in flight, and a ref drops a second tap in the same tick. Every colour comes from the theme tokens.

### Exact alarms: the one switch

`EXACT_ALARM_PERMISSION` in `app.config.ts` is the only place the exact-alarm permission is chosen; `android.permissions` is built from it. It is `USE_EXACT_ALARM` (granted at install; fine for a sideloaded app). For a Play Store release, switch it to `SCHEDULE_EXACT_ALARM` and add a grant prompt. With either permission, expo-notifications 58 arms `DATE` triggers with `setExactAndAllowWhileIdle` (Doze-safe); it re-arms them after a reboot itself.

### Test mode (development build only)

`app/debug/test-mode.tsx`, linked from Today only when `APP_VARIANT` is `development` (`extra.appVariant`, read with `expo-constants`). Settings sets the schedule now, but only within 15–120 min; Test mode stays as a dev-only page for 2-minute Reminders. On: Interval 2 min, Snooze delay 1 min, Active Hours 00:00–24:00 every day and 3 Exercises per Suggestion, then a Rearm, so a Reminder arrives within 2 minutes (a snoozed one is back within 1) through the real core path. Off: only those four fields go back to `defaultSettings`; every other setting (Suggestions, What I can do, Appearance, `excluded`) is kept. With the window all day, Missed at closing and dropped can't be seen in test mode; Missed on replacement can. It also has a 1 / 3 choice of Exercises per Suggestion (`exercisesPerSuggestion`) for walking the guided flow with one card and with three: choosing re-picks the Suggestions of every Reminder ahead (the Rearm rebuilds every Reminder not yet fired), fired ones keep theirs. An **Empty pool (fallback)** switch: on Excludes every library Id (`excluded`) and Rearms, so every Reminder ahead is a fallback (the guided banner, the notification's fallback line); off restores `excluded: []` and Rearms, keeping every other setting. It still writes settings straight into storage (through `rearmOnOpen`'s `prepare`), because `ChangeSettings` rejects its 2-min Interval and 1-min Snooze delay.

## Exercise Library

The Exercise Library is bundled app data, built at dev time from a vendored source plus our curation files. Nothing in it runs in the app except the generated output.

| Path | What lives there |
|---|---|
| `library/source/exercises.json` | free-exercise-db's `dist/exercises.json`, pinned to one commit and never edited. [`SOURCE.md`](library/source/SOURCE.md) records the commit, date, licence and sha256. |
| `library/curation/<group>.yaml` | One file per group (`base`, `floor`, one per Equipment type), keyed by frozen Id. Only Exercises with an entry ship. Format: [`library/curation/README.md`](library/curation/README.md). |
| `library/photos/<id>/{0,1}.jpg` | The start/end photos of the curated source Exercises, fetched from the pinned commit. |
| `library/library.json`, `library/photos.ts` | **Generated** by `npm run library:build`: the `Exercise[]` and the static photo index (one `require` per photo, so photos ship with EAS Update). Committed; never edit by hand. |
| `tools/library/` | The build (`build.ts`) and draft (`draft.ts`) as pure functions with fixture tests, and the CLI (`cli.ts`, run with `tsx`). |

```sh
npm run library:build            # validate the curation, write library.json and photos.ts; fails on any curation error
npm run library:draft -- <group> # print the uncurated candidates for a group, with the script-filled fields, as YAML
npm run library:photos           # download missing photos of every curated source Exercise at the pinned commit
```

`tools/library/committed.test.ts` rebuilds the library from the files on disk and fails if the committed `library.json` or `photos.ts` is stale, so after changing curation run `npm run library:photos` and `npm run library:build` and commit everything together. It also checks the source file against `SOURCE.md`.

## Lint rules

Two rules guard the architecture, both run by `npm run lint`:

- `core/**` may not import `react`, `react-native`, `expo`, `expo-*` or `@expo/*` (`no-restricted-imports`), and that also covers `require()` and dynamic `import()` (`no-restricted-syntax`).
- Code outside `theme/` may not contain literal colours: hex, `rgb()`/`rgba()`/`hsl()`/`hsla()`, or any string or numeric value given to a `…color` style key or prop (`local/no-literal-colors`, in [`tools/eslint/no-literal-colors.js`](tools/eslint/no-literal-colors.js)). Use `useColors()` from `theme/`. `app.config.ts` is also exempt: it is native config, and the adaptive-icon background is a literal.

Identifiers use US "color" (`useColors`, `backgroundColor`, `no-literal-colors`), following React Native and ESLint convention; prose uses "colour".

## App variants and EAS builds

`app.config.ts` picks the app from `APP_VARIANT`; each [`eas.json`](eas.json) profile sets it.

| EAS profile | `APP_VARIANT` | App name | Android package | Build |
|---|---|---|---|---|
| `preview` | `preview` (also the default when unset) | Activity Reminder | `com.agmarco.activityreminder` | standalone APK, internal distribution |
| `development` | `development` | Activity Reminder (dev) | `com.agmarco.activityreminder.dev` | dev client APK, internal distribution |

The dev app's launcher icon has a plain amber background (the daily app keeps the light-blue grid), so the two are easy to tell apart. Each variant has its own package, so each has its own database.

The two packages differ, so both apps install side by side. Both set `android.allowBackup: true` and `runtimeVersion: { policy: "fingerprint" }`. Check a variant's resolved config with `APP_VARIANT=development npx expo config --type public`.

[`fingerprint.config.js`](fingerprint.config.js) keeps the default (balanced) fingerprint but skips every `package.json` script, so adding or editing a script doesn't change the runtime fingerprint or need a new EAS build.

The app is linked to the EAS project `@agmarco/activity-reminder`: `app.config.ts` sets `owner` and `extra.eas.projectId` (the owner ran `eas init`; a dynamic config can't be written by EAS, so the ID lives there). EAS commands run from `src/`, like everything else. Builds are **owner steps**: `eas build --profile development --platform android` and `eas build --profile preview --platform android` need the Expo account and are run by the owner, not by agents.
