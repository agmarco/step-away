
`APP_VARIANT=development npx expo start` serves JavaScript to the **development** build (a dev client), not to Expo Go, so the dev app must be installed on the phone first. Set the variant: plain `npx expo start` (and `npm start`) resolves the `preview` config, so the dev-only Test mode stays hidden.

The web build no longer bundles since #21: expo-sqlite's web worker imports a `.wasm` file Metro isn't configured to resolve. The target is Android, so there are no web shims; `npx expo export --platform web` fails with `Unable to resolve "./wa-sqlite/wa-sqlite.wasm"`.

## The domain core

`reduce(state, event, deps)` is the only entry point. `CoreState` holds the settings (Active Hours per weekday, Interval, IANA time zone, `snoozeMinutes`: the Snooze delay, and the Suggestion settings: `exercisesPerSuggestion` 1–3, default 1; `bodyAreaMode` `'Weighted' | 'Random' | 'Strict'`, default `'Weighted'`; `difficulty`, the Difficulty ceiling, default `'Intermediate'`; `energetic` and `floor`, default `false`; `equipment`, the Equipment owned, default `[]`; `excluded`, the Excluded Exercise Ids, default `[]`; `doseOverrides`, the Dose overrides keyed by Exercise Id, default `{}`; and `appearance` `'System' | 'Light' | 'Dark'`, the app's colour scheme, default `'System'`), the Reminders (fired ones plus the scheduled chain ahead, each with an Id deterministic from its fire time, a Suggestion snapshot of `{ id, name, dose, cue, bodyArea }` per Exercise (`dose` is the Exercise's override, if it has one, else its library Dose), a status, and optionally `snoozes`, `refiresAt`, `done`, `fallback` (true: nothing matched the settings), `swappedOut` (the Ids swapped out, in Swap order) and `rotation` (on a Strict-built Reminder only, the `BODY_AREAS` index the next Strict Suggestion starts from)), `lastResponseAt`, `lastAppOpenAt`, `goalChanges` (Daily Goal changes `{ from: LocalDate, goal }`, oldest first), `pauses` (the Pause history, `{ from, until }` instants, oldest first and never overlapping; Resume shortens the running one's `until`) `daysOff` (the Days Off, `LocalDate`s in the Settings' time zone, sorted and free of duplicates), `badges` (the Badges unlocked, `{ id, unlockedAt }`, in unlock order, catalogue order within one event; never shrunk) and `achievementsSeenAt` (when Achievements was last opened, or `null` if never). `initialState` has `badges: []` and `achievementsSeenAt: null`.

Reminder statuses: `scheduled` (ahead, or fired with no final Response yet), `done` (with `done: [{ id, name, bodyArea }]`, the Exercises done in Suggestion order, copied from the Suggestion, not the library), `skipped`, `missed` (no Response before a later Reminder fired, or before its day's Active Hours ended) and `dropped` (snoozed, with its re-fire landing at or after its day's window end, so it never re-fires; or the outstanding Reminder when a Pause starts or today is taken off, its pending re-fire cleared and its notification dismissed). Dropped is not Missed and is never counted. A dropped Reminder stores what dropped it in `droppedBy`: `'closing'` (set by `settle`), `'pause'` (a Pause) or `'dayOff'` (taking today off). It is set once and never changed after (later Pauses, Days Off, their Undo, Resume, Swap, Rearm and settling leave it), and present only while the status is `dropped`. Absent on a dropped Reminder means `'closing'`: Reminders dropped before the reason was stored were all re-fires past closing. `dropReason(reminder)` (`types.ts`, next to `Reminder.droppedBy`) reads it that way: `droppedBy`, else `'closing'`.

**Settling.** No JavaScript runs when a scheduled notification fires, so Missed and dropped can't be recorded at fire time. Every event first runs `settle(state, now)`, which derives them from the clock, comparing each Reminder's effective fire (`refiresAt ?? firesAt`): dropped at closing (`droppedBy: 'closing'`), Missed on replacement, Missed at closing. The window end is exclusive.

| Event | What it does |
|---|---|
| `AppOpened` | Records `lastAppOpenAt`. |
| `Rearm { timeZone? }` | JS is running: rebuilds the chain of upcoming Reminders over the next 7 days of Active Hours, at most 100 (`MAX_CHAIN`; no-Response fallbacks one Interval apart) and, when given, adopts the device time zone. Every Reminder not yet fired gets its Suggestion rebuilt under the current settings, in fire order, as if built when it fires (see **Suggestion rules**); fired Reminders stay as they are, Suggestion included. With nothing eligible and no fallback candidate either, nothing is scheduled. |
| `Response { reminderId, kind: 'Done', did }` | The guided flow's result, a final Response. Same guard as Skip. Keeps only the Ids in `did` that are in the Reminder's Suggestion, once each, in Suggestion order: with at least one the Reminder becomes `done` with their snapshots; with none (every card was Not this one) it is exactly a Skip. Either way `lastResponseAt` is now and the chain is rebuilt from now, then Badges are evaluated (see **Achievements**). |
| `Response { reminderId, kind: 'Skip' }` | A guarded Skip: accepted only for the outstanding Reminder (the latest fired one by effective fire, still `scheduled`, whether or not a Snooze re-fire is pending); the chain is rebuilt from the Skip time. A Done or Skip before a pending re-fire cancels it: `refiresAt` is cleared, `snoozes` kept, and the re-fire is not scheduled. A Reminder whose re-fire lands past closing stays outstanding until its day's window end. Anything else (duplicate, not fired, superseded, unknown, Missed, dropped) is a no-op that only dismisses the notification and returns the input state. An accepted Skip evaluates Badges (see **Achievements**); a Snooze never does. |
| `Response { reminderId, kind: 'Snooze' }` | Not a final Response (`lastResponseAt` unchanged). Same guard, plus `canSnooze`: no re-fire pending and fewer than 2 Snoozes so far. Re-fires the **same** Reminder (same Id and Suggestion) at now + `snoozeMinutes` and counts the Snooze; the next fallback Reminder comes one Interval after the re-fire. The re-fire's notification says it was snoozed and, after the 2nd Snooze, offers only Start and Skip. A re-fire at or after window end is never scheduled; it settles as dropped. |
| `GuidedStarted { reminderId }` | The guided screen opened on this Reminder. Not a Response: `lastResponseAt` and `snoozes` stay. If it is the outstanding Reminder and its Snooze re-fire is pending, `refiresAt` is cleared and the chain is rebuilt without the re-fire; the chain then counts from the Reminder's own fire time (or `lastResponseAt`, if later), so the next fallback is the first grid time after now. The Reminder stays outstanding until the next one fires; leaving the guided screen doesn't bring the re-fire back. Anything else (not outstanding, no re-fire pending, unknown) returns the input state unchanged with no intents; no dismissal, the screen has already dismissed the notification. |
| `SetDailyGoal { goal }` | Records `{ from: tomorrow, goal }` (tomorrow in the Settings' time zone), replacing any change dated tomorrow or later, so today's goal never moves. A goal that isn't a whole number of at least 1 returns the input state. No intents. |
| `Swap { reminderId, exerciseId }` | Swap on the guided card. Not a Response. Settled first, it is accepted on the Reminders `guidedStart` opens (the outstanding one, or one of today's fired Reminders that settles as Missed or dropped), and only for an `exerciseId` in its Suggestion. The replacement (see **Suggestion rules**) takes its place, and the old Id is appended to `swappedOut`. `lastResponseAt`, `snoozes`, `refiresAt` and `rotation` stay; the chain ahead is rebuilt (only a `ScheduleChain` intent), so a pending Snooze re-fire carries the swapped Suggestion. With no candidate, or anything else, it returns the input state with no intents. |
| `Correct { reminderId, to: 'Done' \| 'Skip' \| 'Missed', did? }` | A correction from Today (or a late guided finish, see `guidedFinish` below), history only: accepted only for a Reminder of today (by its first fire) whose settled status is `done`, `skipped`, `missed` or `dropped` (so a fired Reminder superseded but not yet persisted, settling as Missed, can be corrected). To Done keeps the Ids in `did` that are in the Suggestion, as a Done Response does; with none left it is rejected, not turned into a Skip. To Skip or Missed removes the `done` list. Every correction moves the Reminder out of `dropped`, so `droppedBy` is removed. Only the outcome changes: `lastResponseAt`, `snoozes`, `refiresAt` and the chain stay, and nothing is scheduled. An accepted correction, of any outcome, evaluates Badges (see **Achievements**), so its only intents are `BadgesUnlocked` and `CelebrationDue`. Anything else (a past day, the outstanding Reminder, not fired yet, unknown) returns the input state. |
| `ChangeSettings { change }` | A settings change (`core/settingsChange.ts`): `change` is any subset of the settings but `timeZone`; a field it has replaces the whole field (all of `excluded`, all of `doseOverrides`). Validated first: Interval 15–120 in steps of 5; Snooze delay 5, 10, 15, 20 or 30; Exercises per Suggestion an integer 1–3; `bodyAreaMode`, `difficulty` and `appearance` in their enums; `equipment` a duplicate-free subset of `EQUIPMENT`; `excluded` strings; `doseOverrides` a plain object (not an array, not null) whose every value is a Dose with exactly `kind` (`'reps'` or `'seconds'`), `amount` (an integer 1–999) and `eachSide` (a boolean), its keys any strings, not checked against the library; `energetic` and `floor` booleans; `activeHours` a complete record of the 7 weekdays, each `null` or an integer `{ start, end }` with `0 ≤ start < end ≤ 1440` (all days off is allowed). Any other key, `timeZone` included, makes it invalid. An invalid change returns the input state with no intents. Otherwise, settled, the change is merged into the settings and the chain is rebuilt (only a `ScheduleChain` intent, even for a Suggestion-only or Appearance-only change): the chain ahead runs from its anchor plus k × the Interval as if always set, and if that grid's next time is already past, the next Reminder is the first grid time after now (no catch-up fire). Fired Reminders keep their Suggestions, the outstanding one included; the next Snooze uses the new delay, and a re-fire already pending keeps its time. |
| `Pause { length: 'hour' \| 'twoHours' \| 'restOfToday' }` | Pause Reminders from now. Rejected on a Day Off (input state, no intents). Settled, the outstanding Reminder (if any) becomes `dropped` with `droppedBy: 'pause'` and `refiresAt` cleared and a `DismissNotification` for it; the Pause `{ from: now, until }` is recorded, `until` being now + 60 or 120 minutes or, for `restOfToday`, the next local midnight; a Pause already running keeps its `from` and takes the new `until` (no second entry). Then the chain is rebuilt (see **Pause and Day Off in the chain**). The launcher shortcuts (#45) send it unchanged, through the `pause/[length]` deep link; `pauseLengthOf(value)` (`types.ts`, next to `PauseLength`) checks a length from outside the app: the `PauseLength` for exactly `'hour'`, `'twoHours'` or `'restOfToday'`, `undefined` for anything else (another string, an array, a number, `undefined`). |
| `Resume` | Ends the running Pause (`from <= now < until`): its `until` becomes now, then the chain is rebuilt (only a `ScheduleChain` intent). With no Pause running it returns the input state with no intents. |
| `SetDayOff { date, off }` | Marks `date` (today or later, Settings' time zone: `canSetDayOff`) a Day Off, or undoes it. Rejected (input state, no intents) for a past date, for setting off a day already off, and for undoing a day not off. Taking today off drops the outstanding Reminder as a Pause does (with its dismissal), with `droppedBy: 'dayOff'`. The date is added or removed (`daysOff` stays sorted, no duplicates), then the chain is rebuilt; undoing today brings back today's chain by the usual anchor rules, from now. |
| `AchievementsOpened` | Achievements was opened: settled, `achievementsSeenAt` becomes now (`lastAppOpenAt` is untouched), which clears the new-Badge dot (`hasNewBadge`). No intents, and no Badge evaluation. |
| `ResetSettings` | Reset settings to defaults. Settled, the settings become `defaultSettings` with the current `timeZone` kept (so no Exclusions and no Dose overrides), and the Daily Goal returns to `DEFAULT_DAILY_GOAL` from tomorrow by the `SetDailyGoal` rule; then the chain is rebuilt (only a `ScheduleChain` intent). The Activity Log is never touched: fired Reminders (the outstanding one too), `lastResponseAt`, `lastAppOpenAt` and past `goalChanges` stay. |

**Pause and Day Off in the chain** (`chainTimes`, `schedule.ts`).
- A Day Off has no Reminders.
- No Reminder fires inside a Pause `[from, until)`. Walking each day's grid, a Pause that overlaps the gap before the next time (after the anchor or the previous time, up to and including the next one) moves the anchor to its `until`: the first Reminder after a Pause is `until` + Interval, not the old grid, and nothing more that day if that is at or past the window end. Resume early is the same rule with the shortened `until`.
- The chain built when the Pause starts already holds the times after it, since no JavaScript runs when a Pause ends; a Rearm after the end gives the same times. `restOfToday` ends at midnight, so the next day starts as usual (window start + Interval).

**Suggestion rules** (`suggest.ts` and `swap.ts`, tested through `reduce`; all randomness from the injected `Random`).
- Eligible pool: Difficulty at or below the ceiling (Beginner < Intermediate < Expert), Energetic only when `energetic`, Position Floor only when `floor`, no Equipment or owned Equipment, minus `excluded`.
- Areas first. Weighted picks a Body Area among those with a candidate, at weight 3 if the Reminder's day (Settings' time zone) has no Done Exercise in it and 1 otherwise (coverage is the `done` lists of that day's `done` Reminders), then an Exercise uniformly within it. Random does the same with every area at weight 1. Strict takes the next N areas in `BODY_AREAS` order that have something in the pool, wrapping, from the `rotation` of the latest earlier Reminder that has one (else 0), and picks within each; it advances on every Suggestion, whatever the Response. Within a Suggestion each Exercise is from a different area while it can, and never twice.
- Dose: each Exercise is snapshotted with `doseOf`, its override if it has one, else its library Dose, in the chain ahead, the fallback and Swap alike. A fired Reminder keeps its snapshot, so a later override change doesn't touch it.
- No-repeat window: the Exercises of the last 5 Suggestions, swapped-out ones included.
- Relaxation, in order: repeated areas (as many distinct as possible); the window shrinks one step at a time from 5 to 1, keeping the largest that gives the full count; fewer Exercises; in Strict, when its areas have nothing left even at window 1, the rest of the pool drawn as Random would (the rotation still advances); window 0 only when the whole pool was in the previous Suggestion.
- Fallback, only when the pool is empty: the gentle base Exercises (no Equipment, Position not Floor, Beginner, not Energetic), or the whole base set when there are none, ignoring Exclusions, through the same rules with a count of 1 (the window, the mode and, in Strict, the rotation); the Reminder carries `fallback: true`.
- Swap's replacement, under the current settings, from the pool (the fallback set for a fallback Reminder): not in the window before this Reminder, this Suggestion or its `swappedOut`. Preference: the same Body Area, then an area not elsewhere in the Suggestion, then any; areas first at weight 1 within that. With nothing left the window shrinks step by step to 0, then swapped-out Exercises come back; never one already in the Suggestion.

**Days, Daily Goal and Streak** (`days.ts`, derived, never stored). A Reminder belongs to the local date (Settings' time zone) of its `firesAt`, its first fire; a Snooze re-fire doesn't move it.
- `dailyGoalFor(state, date)`: the last `goalChanges` entry with `from` on or before `date`, else `DEFAULT_DAILY_GOAL` (4).
- `reachesDailyGoal(state, date, done)`: the Goal Day rule, `done` ≥ that day's goal; the one place it lives (`isGoalDay`, `isGoalDayIn` and Perfect day go through it; `streak`, `weekMarks`, `monthMarks` and `longestStreak` through `isGoalDayIn`).
- `isGoalDay(state, date)`: the day's `done` Reminders reach that day's goal (`reachesDailyGoal` on `dayTally`). It and `dayTally` scan every Reminder, so they are for a single day (Today, History's day panel).
- `logByDay(state)` (internal to the core, not in `index.ts`): the Activity Log by day, built in one pass over the Reminders: `days`, a `LoggedDay` `{ date, done, skipped, missed, areas }` per day that has a Reminder (any status), keyed by `dateKey`, and `earliest`, the earliest Reminder's day as a `LocalDate` (undefined with no Reminders). `streak`, `weekMarks`, `monthMarks`, `historyRange`, `records` and Badge evaluation build it once per call and look each day up, so judging many days costs one pass plus one step per day. `isGoalDayIn(state, log, date)` (also internal): whether a day is a Goal Day, `reachesDailyGoal` on its Done count in `log` (0 for a day without Reminders); `streak`, `weekMarks`, `monthMarks` and `longestStreak` judge each day with it.
- `dayTally(state, date)` / `todayTally(state, now)`: `{ done, skipped, missed, exercises }`, `exercises` being the total length of the day's `done` lists. Dropped and still-`scheduled` Reminders aren't counted.
- `streak(state, now)`: consecutive Goal Days backwards. Today counts if it is already a Goal Day; otherwise the count starts from yesterday, so an unfinished today doesn't break it. Days Off and days without Active Hours (by the current Settings' weekdays) are skipped, even one that reached its goal. A Pause gets nothing special: a paused day is judged as usual. The first earlier day with Active Hours that isn't a Goal Day ends it; it looks back no further than the earliest Reminder's day. Each day is judged from `logByDay`.
- `weekMarks(state, now)`: Mon–Fri of the current week (Monday to Sunday, so on a weekend the whole past Mon–Fri), a `MarkedDay` `{ date, mark }` per day, the `mark` a `DayMark` chosen by precedence `today` (even if already a Goal Day or a Day Off), `dayOff`, `future`, `none` (a past day before the earliest Reminder's day, or any past day when there are no Reminders: no data yet), `off` (no Active Hours), `goal`, else `missed`.
- `monthMarks(state, month, now)`: every date of `month`, a `YearMonth` `{ year, month }` (`month` 1–12), in order, a `MarkedDay` per day by the same rule as `weekMarks`, judged from `logByDay`; the History calendar.
- `historyRange(state, now)`: `{ first, last }`, the `YearMonth`s History can show: from the month of the earliest Reminder's day (the current month when there are no Reminders or that is later) to 12 months past the current month.
- `addMonths(month, n)`: the `YearMonth` `n` months after `month` (before it when `n` is negative), across year ends; `historyRange` and History's month steps go through it.
- `monthBefore(a, b)` / `sameMonth(a, b)`: whether `YearMonth` `a` comes strictly before `b`, and whether they are the same month, across year ends; a `LocalDate` passes as its month (`sameMonth(month, today)`).
- `sameDate(a, b)`: whether two `LocalDate`s are the same calendar date.
- `dateKey(date)`: a number that orders `LocalDate`s (YYYYMMDD).
- `isDayOff(state, date)`: whether `date` is a Day Off (in `daysOff`).
- `canSetDayOff(state, date, now)`: the Day Off date rule, `date` is today or later (the local date of `now`, Settings' time zone), so a Day Off can be set or undone for it; a day already past can't. `SetDayOff` goes through it.

**Achievements** (`achievements.ts`, tested through `reduce` and its exports). `BADGES` is the Badge catalogue, in order, each `{ id, group, threshold? }`: Streak (`streak-3`, `-7`, `-14`, `-30`, `-60`, `-100`), Total Done (`done-1`, `-10`, `-50`, `-100`, `-250`, `-500`), Variety (`variety-10`, `-25`, `-50`) and One-day (`balance`, `perfect-day`). It is the one source of the `BadgeId` type; labels are the screen's job.
- `records(state, now)`: `{ longestStreak, mostDoneInDay, mostDoneInWeek }`, recomputed on every call, all 0 on an empty Activity Log. `longestStreak` is the longest run of Goal Days under the `streak` rules (Days Off and days without Active Hours by the current Settings skipped; a today not yet a Goal Day doesn't end a run), so never less than `streak`. `mostDoneInDay` and `mostDoneInWeek` are the most Done Reminders in one day and in one local Monday–Sunday week, every day counted, Days Off and weekends included. A correction can lower them.
- Badge evaluation, inside `reduce`, after an accepted Done or Skip Response and an accepted `Correct` (any outcome), against the resulting state; nothing else evaluates (Snooze, Swap, settings, Pause, Day Off, AchievementsOpened, rejected events). Every Badge met and not held is appended with `unlockedAt` = now, in catalogue order. Streak N: `longestStreak` ≥ N. Total Done N: ≥ N `done` Reminders. Variety N: ≥ N distinct Exercise Ids across every `done` list. Balance: some day whose `done` lists cover all six `BODY_AREAS`. Perfect day: some day (today so far included) whose Done count reaches that day's Daily Goal with no skipped or Missed Reminder; dropped and still-`scheduled` ones are ignored. Badges are never revoked: a later Skip, Missed or correction leaves them.
- The intents, after the event's own: `BadgesUnlocked` when a Badge is new, then `CelebrationDue` when the event recorded a Done and either a Badge is new or `goalReached`: today's Done count (the local date of now) was below today's Daily Goal on the settled state before the event and is at or above it after. A Done-to-Done correction counts as recording a Done, but crosses no goal.
- `isNewBadge(badge, seenAt)`: whether a held Badge is New, the one rule for it: `seenAt` is `null` (Achievements never opened) or the Badge's `unlockedAt` is strictly after `seenAt`. The Achievements page's New marks use it with the previous visit.
- `hasNewBadge(state)`: the new-Badge dot: `isNewBadge` holds for some Badge against `achievementsSeenAt`.

**Pause and Day Off on Today** (`pause.ts`, tested).
- `heroStatus(state, now, notifications?)`: `{ kind: 'off' }` (Reminders are off: notifications blocked), `{ kind: 'dayOff' }`, `{ kind: 'paused', until }`, `{ kind: 'next', at, snoozed }` (`at` is the re-fire time when `snoozed`) or `{ kind: 'none' }`. When states overlap: `off` > `dayOff` > `paused` > `next` > `none`; a Pause not started yet isn't `paused`. `notifications` is a `NotificationsState`, `'allowed'` or `'blocked'`; absent means `'allowed'`. It is a device fact the adapters read, never stored in `CoreState`; nothing else in the core reads it, so scheduling (the chain, Rearm) is the same either way.
- `canPause(state, now, status = heroStatus(state, now))`: whether a Pause would do something, so the hero offers it (the hero passes the `status` it already has; the default status assumes notifications allowed, so only a passed status can be `off`). False for `off`, `dayOff` and `paused`. Otherwise true whenever a Reminder is outstanding (`outstandingReminder`), which the Pause drops, under `next` or `none`; and under `next` when that next Reminder (its re-fire time when snoozed) falls on today in the Settings' time zone. False under `none` with nothing outstanding, and after the day's last Reminder with nothing outstanding (a Pause would only record a line).
- `pausesOn(state, date)`: the Pauses whose `from` falls on `date` (Settings' time zone), oldest first; History's day panel. `todaysPauses(state, now)` is `pausesOn` of today, for Today's inline Pause lines.
- `isRunning(pause, now)`: `from <= now < until`, the one rule for a running Pause (`runningPause`, and through it `heroStatus` and the Pause event, and Today's Pause line use it).
- `endsAtMidnight(until, timeZone)`: whether `until` is a local midnight in `timeZone` (`instantAt` of its own date at 00:00), as a Pause for the rest of today ends.

The chain is scheduled ahead because expo-notifications runs no JavaScript when a scheduled notification fires (see #21, "Owner decision: schedule the chain ahead"). Fired Reminders with no Response stay in the shade, bundled in one group, until JS next runs and dismisses the stale ones.

### Exact alarms: the one switch

`EXACT_ALARM_PERMISSION` in `app.config.ts` is the only place the exact-alarm permission is chosen; `android.permissions` is built from it. It is `USE_EXACT_ALARM` (granted at install; fine for a sideloaded app). For a Play Store release, switch it to `SCHEDULE_EXACT_ALARM` and add a grant prompt: its slot is onboarding's Permissions step, behind `exactAlarmGrantNeeded()` (`notificationPermission.ts`). It reads the built config's `android.permissions` at runtime from `expo-constants` (`Constants.expoConfig?.android?.permissions`, the strings as `app.config.ts` lists them, today `['USE_EXACT_ALARM']`), not `app.config.ts` itself, which stays out of the app bundle; `exactAlarmGrantNeededFor` (`exactAlarm.ts`) decides, so it is false while the list has `USE_EXACT_ALARM`. With either permission, expo-notifications 58 arms `DATE` triggers with `setExactAndAllowWhileIdle` (Doze-safe); it re-arms them after a reboot itself.

**Permission re-grant needs no re-arm today.** `USE_EXACT_ALARM` is granted at install and can't be revoked, and scheduling never reads the notification permission (#31: Reminders stay scheduled while notifications are blocked, see Today's Notifications banner), so granting a permission again changes no alarm. If the switch moves to `SCHEDULE_EXACT_ALARM`, the user can revoke and re-grant "Alarms & reminders", and re-arming on that grant must be handled: expo-notifications doesn't listen for the exact-alarm grant broadcast (`ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`).

## Exercise Library

The Exercise Library is bundled app data, built at dev time from a vendored source plus our curation files. Nothing in it runs in the app except the generated output.

| Path | What lives there |
|---|---|
| `library/source/exercises.json` | free-exercise-db's `dist/exercises.json`, pinned to one commit and never edited. [`SOURCE.md`](library/source/SOURCE.md) records the commit, date, licence and sha256. |
| `library/curation/<group>.yaml` | One file per group (`base`, `floor`, and one per Equipment type: `dumbbells`, `resistance-bands`), keyed by frozen Id. Only Exercises with an entry ship. Format: [`library/curation/README.md`](library/curation/README.md). |
| `library/photos/<id>/{0,1}.webp` | The start/end photos of the curated source Exercises, fetched from the pinned commit and compressed to WebP. |
| `library/library.json`, `library/photos.ts` | **Generated** by `npm run library:build`: the `Exercise[]` and the static photo index (one `require` per photo, so photos ship with EAS Update). Committed; never edit by hand. |
| `tools/library/` | The build (`build.ts`), draft (`draft.ts`) and photo step (`photos.ts`) as functions with fixture tests, and the CLI (`cli.ts`, run with `tsx`). |

```sh
npm run library:build            # validate the curation, write library.json and photos.ts; fails on any curation error
npm run library:draft -- <group> # print the uncurated candidates for a group, with the script-filled fields, as YAML
npm run library:photos           # download and compress the missing photos of every curated source Exercise at the pinned commit
```

Photos are compressed as they are downloaded (`tools/library/photos.ts`); no source JPEG is written to disk. Each photo is shrunk to just cover a 440×294 box at its own aspect ratio (never enlarged, never cropped) and encoded as lossy WebP at quality 60 and effort 6, with no metadata. The screens show photos cover-fit in an 850:567 box at most about 443 physical px wide (the Exercise card), so this is about 1:1 on screen; the settings were picked in #59 (all 400 photos are about 3 MiB, down from 17.6 MiB). WebP won over JPEG: at the same 440 px width and quality 60, a mozjpeg JPEG came to 3.91 MiB and showed blocking, and Metro and React Native load WebP on Android with no native change. A photo key stays the source path, `<id>/0.jpg`, in `library.json` and the photo index; only its bundled file is `<id>/0.webp` (`photoFile`, in the sharp-free `tools/library/mapping.ts`). `sharp` is pinned to an exact version, and the step is deterministic: the same source gives the same bytes on every run, and `library:photos` skips a photo whose `.webp` is already there. A golden hash in `photos.test.ts` fails if a sharp upgrade changes the output; then redo the photos: delete `library/photos/`, run `npm run library:photos` and `npm run library:build`, update the hash and commit the photos together.

Steps never carry a count or any number: the Dose, which the user can change, carries it ([`DRAFTING.md`](library/curation/DRAFTING.md) section 7). The build fails on a digit in any step, naming the Id and the step.

`tools/library/committed.test.ts` rebuilds the library from the files on disk and fails if the committed `library.json` or `photos.ts` is stale, so after changing curation run `npm run library:photos` and `npm run library:build` and commit everything together. It also checks the source file against `SOURCE.md`.

## Lint rules

Two rules guard the architecture, both run by `npm run lint`:

- `core/**` may not import `react`, `react-native`, `expo`, `expo-*` or `@expo/*` (`no-restricted-imports`), and that also covers `require()` and dynamic `import()` (`no-restricted-syntax`).
- Code outside `theme/` may not contain literal colours: hex, `rgb()`/`rgba()`/`hsl()`/`hsla()`, or any string or numeric value given to a `…color` style key or prop (`local/no-literal-colors`, in [`tools/eslint/no-literal-colors.js`](tools/eslint/no-literal-colors.js)). Use `useColors()` from `theme/`. `app.config.ts` is also exempt: it is native config, and the adaptive-icon background is a literal.

Identifiers use US "color" (`useColors`, `backgroundColor`, `no-literal-colors`), following React Native and ESLint convention; prose uses "colour".

The dev app's launcher icon has a plain amber background (the daily app keeps the light-blue grid), so the two are easy to tell apart. Each variant has its own package, so each has its own database.

The two packages differ, so both apps install side by side. Both set `android.allowBackup: true` and `runtimeVersion: { policy: "fingerprint" }`. Check a variant's resolved config with `APP_VARIANT=development npx expo config --type public`.

[`fingerprint.config.js`](fingerprint.config.js) keeps the default (balanced) fingerprint but skips every `package.json` script, so adding or editing a script doesn't change the runtime fingerprint or need a new EAS build.

The app is linked to the EAS project `@agmarco/activity-reminder`: `app.config.ts` sets `owner` and `extra.eas.projectId` (the owner ran `eas init`; a dynamic config can't be written by EAS, so the ID lives there). EAS commands run from `src/`, like everything else. Builds are **owner steps**: `eas build --profile development --platform android` and `eas build --profile preview --platform android` need the Expo account and are run by the owner, not by agents.

### EAS Update and when to rebuild

The `preview` app gets JavaScript and asset changes over the air with EAS Update; the dev app never does (it loads JS from the dev server).

- **Config.** `expo-updates` is installed and **configured, not imported**: no app code imports it, so the current dev build, which doesn't have its native module, keeps running from the dev server. `app.config.ts` sets `updates` per variant: for `preview`, `enabled: true`, `url: https://u.expo.dev/<extra.eas.projectId>`, `checkAutomatically: 'ON_LOAD'` and `fallbackToCacheTimeout: 0`; for `development`, `enabled: false`. The `expo-updates` config plugin writes these to the Android manifest (`expo.modules.updates.ENABLED`, `EXPO_UPDATE_URL`, `EXPO_UPDATES_CHECK_ON_LAUNCH` `ALWAYS`, `EXPO_UPDATES_LAUNCH_WAIT_MS` `0`, `EXPO_RUNTIME_VERSION`).
- **Channel.** The `preview` profile in `eas.json` sets `"channel": "preview"`, so the `preview` build asks for updates on that channel. The `development` profile has no channel.
- **Check on launch, apply on next launch.** At each launch the app starts with the JS it has (the APK's, or the last update it downloaded) and checks the channel in the background without waiting (timeout 0). A new update is downloaded then and runs from the **next** launch (close the app from Recents and open it again).
- **Runtime guard.** `runtimeVersion: { policy: 'fingerprint' }`: the runtime version is a hash of the native project (native modules and their versions, config plugins and the native fields of `app.config.ts`, with `fingerprint.config.js`'s skips). A build only takes updates with its own runtime version, so an update published from JS that needs different native code is ignored by the old build.
- **Publish (owner step, from `src/`):** `APP_VARIANT=preview npx eas-cli@latest update --channel preview --environment preview --message "<what changed>"`. `--environment preview` is required: without it, a non-interactive `eas update` stops with "The `--environment` flag must be set". Like builds, this needs the Expo account and is never run by agents.

**Rebuild or update?**

| Change | Ships with |
|---|---|
| JS or TypeScript under `app/`, `screens/`, `core/`, `platform/`, `theme/`; the Exercise Library output; images and other assets | **EAS Update** |
| Adding, removing or upgrading a package with native code (an `expo-*` module, `react-native`), an `expo` SDK upgrade | **New EAS build** |
| A config plugin, built-in or local (`plugins/`, e.g. the launcher shortcuts), or its options | **New EAS build** |
| Android permissions (e.g. `EXACT_ALARM_PERMISSION`), and other native `app.config.ts` fields: `android.*`, `scheme`, `name`, icons, `userInterfaceStyle`, `updates` | **New EAS build** |
| A build profile's `channel` or `env` in `eas.json` (e.g. `APP_VARIANT`) | **New EAS build**: they are baked into the build when it is made, and the fingerprint doesn't see them |
| `package.json` scripts, docs, tests, other `eas.json` edits (e.g. a new profile) | Neither (not in the app; skipped by the fingerprint) |

**How to tell:** the fingerprint. From `src/`, `APP_VARIANT=preview npx expo-updates fingerprint:generate --platform android` prints the current native project's fingerprint as JSON (its `hash` is the runtime version). If it equals the installed build's runtime version (on its EAS build page, or `npx eas-cli@latest update:list --branch preview`), an EAS Update reaches the phone; if it differs, the change needs a new EAS build, and an update published now would be ignored by the installed app. `npx eas-cli@latest fingerprint:compare` (Expo account) compares against a build directly.

The phone checks for this build (re-arm after reboot and after installing over the old build, Doze, shade taps, EAS Update, light/dark, the launcher shortcuts) are in [`../docs/device-checklist.md`](../docs/device-checklist.md).

### Launcher shortcuts

Long-press the app icon for three static Android shortcuts: **Pause 1 h**, **Pause 2 h** and **Pause today** (long labels "Pause for 1 hour", "Pause for 2 hours", "Pause for the rest of today"). Tapping one opens Today, paused.

- **The config plugin** ([`plugins/withPauseShortcuts.ts`](plugins/withPauseShortcuts.ts)), added to `plugins` in `app.config.ts` with the variant's `scheme` and `package`, writes `res/xml/shortcuts.xml` (`pauseShortcutsXml`): the shortcuts `pause_hour`, `pause_two_hours` and `pause_rest_of_today`, each with the app icon (`@mipmap/ic_launcher`) and one `android.intent.action.VIEW` intent whose `android:data` is `<scheme>://pause/<length>` and whose `android:targetPackage` / `android:targetClass` are the variant's package and its `MainActivity`. It adds the six labels to `res/values/strings.xml` (`addPauseShortcutStrings`, named `<shortcut id>_short` / `_long`) and an `android.app.shortcuts` meta-data pointing at `@xml/shortcuts` to the launcher `MainActivity` (`addShortcutsMetaData`, added once). So the preview app's shortcuts open `activityreminder://pause/…` in `com.agmarco.activityreminder`, the dev app's `activityreminder-dev://pause/…` in `com.agmarco.activityreminder.dev`. It is a native change: the shortcuts reach the phone with the next EAS build. Check the output with a local `APP_VARIANT=development npx expo prebuild --platform android --no-install --clean` (no Expo account needed; `android/` is gitignored, delete it after, and revert the `android` script prebuild rewrites in `package.json`).
- **The deep link** (`app/pause/[length].tsx`): a valid length (`pauseLengthOf`) calls the handler's `pause` once per opening (a ref guards re-renders and a second effect run), then `router.dismissTo('/')` goes to Today: back to it when it is under the link, in the link's place on a cold start. Today shows "Paused until…" through its usual path. A Pause the core rejects (on a Day Off) is a no-op, and an unknown length only goes to Today. The scheme already exists in both variants, so the links work on an installed build without the shortcuts, e.g. `adb shell am start -f 0x1000c000 -a android.intent.action.VIEW -d "activityreminder-dev://pause/hour" -n com.agmarco.activityreminder.dev/.MainActivity`. The flags are the shortcuts' own (`NEW_TASK | CLEAR_TASK | TASK_ON_HOME`, see `adb shell dumpsys shortcut`): without them, a task left in Recents swallows the link (`am start` only brings the old task to the front).
