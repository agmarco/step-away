## Commands

```sh
npm install          # or npm ci
npm test             # Vitest: **/*.test.ts in Node (the domain core, the library build, theme/contrast.test.ts, platform/db.test.ts, platform/store.test.ts, platform/suggestionBackfill.test.ts, platform/exactAlarm.test.ts and platform/trace.test.ts, the Settings page's helpers in screens/settings/, screens/today/pauseDisplay.test.ts and plugins/withPauseShortcuts.test.ts)
npm run typecheck    # tsc --noEmit
npm run lint         # ESLint: Expo rules, the core import rule, the no-literal-colours rule
APP_VARIANT=development npx expo start   # dev server; open it in the "Activity Reminder (dev)" app
npm run web          # web: currently does not bundle (see below)
```

`APP_VARIANT=development npx expo start` serves JavaScript to the **development** build (a dev client), not to Expo Go, so the dev app must be installed on the phone first. Set the variant: plain `npx expo start` (and `npm start`) resolves the `preview` config, so the dev-only Test mode stays hidden.

The web build no longer bundles since #21: expo-sqlite's web worker imports a `.wasm` file Metro isn't configured to resolve. The target is Android, so there are no web shims; `npx expo export --platform web` fails with `Unable to resolve "./wa-sqlite/wa-sqlite.wasm"`.

## The domain core

`reduce(state, event, deps)` is the only entry point. `CoreState` holds the settings (Active Hours per weekday, Interval, IANA time zone, `snoozeMinutes`: the Snooze delay, and the Suggestion settings: `exercisesPerSuggestion` 1–3, default 1; `bodyAreaMode` `'Weighted' | 'Random' | 'Strict'`, default `'Weighted'`; `difficulty`, the Difficulty ceiling, default `'Intermediate'`; `energetic` and `floor`, default `false`; `equipment`, the Equipment owned, default `[]`; `excluded`, the Excluded Exercise Ids, default `[]`; and `appearance` `'System' | 'Light' | 'Dark'`, the app's colour scheme, default `'System'`), the Reminders (fired ones plus the scheduled chain ahead, each with an Id deterministic from its fire time, a Suggestion snapshot of `{ id, name, dose, cue, bodyArea }` per Exercise, a status, and optionally `snoozes`, `refiresAt`, `done`, `fallback` (true: nothing matched the settings), `swappedOut` (the Ids swapped out, in Swap order) and `rotation` (on a Strict-built Reminder only, the `BODY_AREAS` index the next Strict Suggestion starts from)), `lastResponseAt`, `lastAppOpenAt`, `goalChanges` (Daily Goal changes `{ from: LocalDate, goal }`, oldest first), `pauses` (the Pause history, `{ from, until }` instants, oldest first and never overlapping; Resume shortens the running one's `until`) and `daysOff` (the Days Off, `LocalDate`s in the Settings' time zone, sorted and free of duplicates).

Reminder statuses: `scheduled` (ahead, or fired with no final Response yet), `done` (with `done: [{ id, name, bodyArea }]`, the Exercises done in Suggestion order, copied from the Suggestion, not the library), `skipped`, `missed` (no Response before a later Reminder fired, or before its day's Active Hours ended) and `dropped` (snoozed, with its re-fire landing at or after its day's window end, so it never re-fires; or the outstanding Reminder when a Pause starts or today is taken off, its pending re-fire cleared and its notification dismissed). Dropped is not Missed and is never counted. A dropped Reminder stores what dropped it in `droppedBy`: `'closing'` (set by `settle`), `'pause'` (a Pause) or `'dayOff'` (taking today off). It is set once and never changed after (later Pauses, Days Off, their Undo, Resume, Swap, Rearm and settling leave it), and present only while the status is `dropped`. Absent on a dropped Reminder means `'closing'`: Reminders dropped before the reason was stored were all re-fires past closing. `dropReason(reminder)` (`types.ts`, next to `Reminder.droppedBy`) reads it that way: `droppedBy`, else `'closing'`.

**Settling.** No JavaScript runs when a scheduled notification fires, so Missed and dropped can't be recorded at fire time. Every event first runs `settle(state, now)`, which derives them from the clock, comparing each Reminder's effective fire (`refiresAt ?? firesAt`): dropped at closing (`droppedBy: 'closing'`), Missed on replacement, Missed at closing. The window end is exclusive.

| Event | What it does |
|---|---|
| `AppOpened` | Records `lastAppOpenAt`. |
| `Rearm { timeZone? }` | JS is running: rebuilds the chain of upcoming Reminders over the next 7 days of Active Hours, at most 100 (`MAX_CHAIN`; no-Response fallbacks one Interval apart) and, when given, adopts the device time zone. Every Reminder not yet fired gets its Suggestion rebuilt under the current settings, in fire order, as if built when it fires (see **Suggestion rules**); fired Reminders stay as they are, Suggestion included. With nothing eligible and no fallback candidate either, nothing is scheduled. |
| `Response { reminderId, kind: 'Done', did }` | The guided flow's result, a final Response. Same guard as Skip. Keeps only the Ids in `did` that are in the Reminder's Suggestion, once each, in Suggestion order: with at least one the Reminder becomes `done` with their snapshots; with none (every card was Not this one) it is exactly a Skip. Either way `lastResponseAt` is now and the chain is rebuilt from now. |
| `Response { reminderId, kind: 'Skip' }` | A guarded Skip: accepted only for the outstanding Reminder (the latest fired one by effective fire, still `scheduled`, whether or not a Snooze re-fire is pending); the chain is rebuilt from the Skip time. A Done or Skip before a pending re-fire cancels it: `refiresAt` is cleared, `snoozes` kept, and the re-fire is not scheduled. A Reminder whose re-fire lands past closing stays outstanding until its day's window end. Anything else (duplicate, not fired, superseded, unknown, Missed, dropped) is a no-op that only dismisses the notification and returns the input state. |
| `Response { reminderId, kind: 'Snooze' }` | Not a final Response (`lastResponseAt` unchanged). Same guard, plus `canSnooze`: no re-fire pending and fewer than 2 Snoozes so far. Re-fires the **same** Reminder (same Id and Suggestion) at now + `snoozeMinutes` and counts the Snooze; the next fallback Reminder comes one Interval after the re-fire. The re-fire's notification says it was snoozed and, after the 2nd Snooze, offers only Start and Skip. A re-fire at or after window end is never scheduled; it settles as dropped. |
| `GuidedStarted { reminderId }` | The guided screen opened on this Reminder. Not a Response: `lastResponseAt` and `snoozes` stay. If it is the outstanding Reminder and its Snooze re-fire is pending, `refiresAt` is cleared and the chain is rebuilt without the re-fire; the chain then counts from the Reminder's own fire time (or `lastResponseAt`, if later), so the next fallback is the first grid time after now. The Reminder stays outstanding until the next one fires; leaving the guided screen doesn't bring the re-fire back. Anything else (not outstanding, no re-fire pending, unknown) returns the input state unchanged with no intents; no dismissal, the screen has already dismissed the notification. |
| `SetDailyGoal { goal }` | Records `{ from: tomorrow, goal }` (tomorrow in the Settings' time zone), replacing any change dated tomorrow or later, so today's goal never moves. A goal that isn't a whole number of at least 1 returns the input state. No intents. |
| `Swap { reminderId, exerciseId }` | Swap on the guided card. Not a Response. Settled first, it is accepted on the Reminders `guidedStart` opens (the outstanding one, or one of today's fired Reminders that settles as Missed or dropped), and only for an `exerciseId` in its Suggestion. The replacement (see **Suggestion rules**) takes its place, and the old Id is appended to `swappedOut`. `lastResponseAt`, `snoozes`, `refiresAt` and `rotation` stay; the chain ahead is rebuilt (only a `ScheduleChain` intent), so a pending Snooze re-fire carries the swapped Suggestion. With no candidate, or anything else, it returns the input state with no intents. |
| `Correct { reminderId, to: 'Done' \| 'Skip' \| 'Missed', did? }` | A correction from Today (or a late guided finish, see `guidedFinish` below), history only: accepted only for a Reminder of today (by its first fire) whose settled status is `done`, `skipped`, `missed` or `dropped` (so a fired Reminder superseded but not yet persisted, settling as Missed, can be corrected). To Done keeps the Ids in `did` that are in the Suggestion, as a Done Response does; with none left it is rejected, not turned into a Skip. To Skip or Missed removes the `done` list. Every correction moves the Reminder out of `dropped`, so `droppedBy` is removed. Only the outcome changes: `lastResponseAt`, `snoozes`, `refiresAt` and the chain stay, and there are no intents. Anything else (a past day, the outstanding Reminder, not fired yet, unknown) returns the input state. |
| `ChangeSettings { change }` | A change on the Settings page (`core/settingsChange.ts`): `change` is any subset of the settings but `timeZone`. Validated first: Interval 15–120 in steps of 5; Snooze delay 5, 10, 15, 20 or 30; Exercises per Suggestion an integer 1–3; `bodyAreaMode`, `difficulty` and `appearance` in their enums; `equipment` a duplicate-free subset of `EQUIPMENT`; `excluded` strings; `energetic` and `floor` booleans; `activeHours` a complete record of the 7 weekdays, each `null` or an integer `{ start, end }` with `0 ≤ start < end ≤ 1440` (all days off is allowed). Any other key, `timeZone` included, makes it invalid. An invalid change returns the input state with no intents. Otherwise, settled, the change is merged into the settings and the chain is rebuilt (only a `ScheduleChain` intent, even for a Suggestion-only or Appearance-only change): the chain ahead runs from its anchor plus k × the Interval as if always set, and if that grid's next time is already past, the next Reminder is the first grid time after now (no catch-up fire). Fired Reminders keep their Suggestions, the outstanding one included; the next Snooze uses the new delay, and a re-fire already pending keeps its time. |
| `Pause { length: 'hour' \| 'twoHours' \| 'restOfToday' }` | Pause Reminders from now. Rejected on a Day Off (input state, no intents). Settled, the outstanding Reminder (if any) becomes `dropped` with `droppedBy: 'pause'` and `refiresAt` cleared and a `DismissNotification` for it; the Pause `{ from: now, until }` is recorded, `until` being now + 60 or 120 minutes or, for `restOfToday`, the next local midnight; a Pause already running keeps its `from` and takes the new `until` (no second entry). Then the chain is rebuilt (see **Pause and Day Off in the chain**). The launcher shortcuts (#45) send it unchanged, through the `pause/[length]` deep link; `pauseLengthOf(value)` (`types.ts`, next to `PauseLength`) checks a length from outside the app: the `PauseLength` for exactly `'hour'`, `'twoHours'` or `'restOfToday'`, `undefined` for anything else (another string, an array, a number, `undefined`). |
| `Resume` | Ends the running Pause (`from <= now < until`): its `until` becomes now, then the chain is rebuilt (only a `ScheduleChain` intent). With no Pause running it returns the input state with no intents. |
| `SetDayOff { date, off }` | Marks `date` (today or later, Settings' time zone) a Day Off, or undoes it. Rejected (input state, no intents) for a past date, for setting off a day already off, and for undoing a day not off. Taking today off drops the outstanding Reminder as a Pause does (with its dismissal), with `droppedBy: 'dayOff'`. The date is added or removed (`daysOff` stays sorted, no duplicates), then the chain is rebuilt; undoing today brings back today's chain by the usual anchor rules, from now. |
| `ResetSettings` | Reset settings to defaults. Settled, the settings become `defaultSettings` with the current `timeZone` kept, and the Daily Goal returns to `DEFAULT_DAILY_GOAL` from tomorrow by the `SetDailyGoal` rule; then the chain is rebuilt (only a `ScheduleChain` intent). The Activity Log is never touched: fired Reminders (the outstanding one too), `lastResponseAt`, `lastAppOpenAt` and past `goalChanges` stay. |

| Intent | Carried out by |
|---|---|
| `ScheduleChain { reminders }` | Replaces the whole scheduled chain: cancel every scheduled notification, schedule these (including any pending Snooze re-fire, whose entry has Start / Skip only after the 2nd Snooze). Each body is one `Name · Dose · Cue` line per Exercise; a fallback Reminder's body ends with the line `No Exercises match your settings`. |
| `DismissNotification { reminderId }` | Removes that Reminder's notification from the shade. |

Also exported: `guidedFinish(state, reminderId, did, now)`, what finishing the guided screen records (`core/guidedFinish.ts`, tested): on the outstanding Reminder, the `Response { kind: 'Done', did }`; otherwise, on the settled state (a replaced Reminder can still be stored as `scheduled`), null for an unknown Reminder, one not fired yet, or one from another day, and else a late answer as a correction of today's Reminder: with at least one Id of `did` in its Suggestion, `Correct { to: 'Done', did }` whatever its settled status (a finish with a Did it is a Done, even over a Skip); with none, null over `done` or `skipped` (no Did its never overwrites an answer) and `Correct { to: 'Skip' }` over Missed or dropped. The newer Reminder stays outstanding and the chain is untouched. `guidedStart(state, reminderId, now)` (same file, tested) is the Reminder the guided screen can open on: the outstanding one, or, on the settled state, one of today's fired Reminders that settled as Missed or dropped (e.g. just replaced by a newer one, or past closing), returned with that settled status; undefined for one already answered (done or skipped), from another day, not fired yet, or unknown. Also: `canSnooze(reminder, now)` (fewer than 2 Snoozes and no re-fire pending: the Snooze guard, and whether the guided screen shows Snooze), `outstandingReminder(state, now)` (the rule the Response guard uses; the adapter uses it to dismiss stale notifications), `isOutstanding(state, reminderId, now)` (whether that Reminder is the outstanding one, tested: the adapter uses it to accept a Done, Skip or Snooze, the guided screen to tell whether Snooze can show, and `guidedFinish` and `guidedStart` to recognise the outstanding Reminder), `todaysReminders(state, now)` (today's fired Reminders in the Settings' time zone, newest first) and `nextReminder(state, now)` (the earliest of the first scheduled Reminder after `now` and any pending Snooze re-fire), both for Today, `settle`, `effectiveFire` and `refireScheduled(reminder, settings, now)` (whether a snoozed Reminder is coming back: its re-fire is ahead and before its day's window end; so Today shows settled statuses and re-fire times, and a re-fire past closing as "Snoozed past closing" straight away), `isReminderId(id)` (tells Reminder notifications from others), `formatDose`, `exerciseGroups(library)` (`core/groups.ts`, tested: `{ floor, equipment }`, whether some Exercise has Position Floor and the Equipment some Exercise needs, in `EQUIPMENT` order; the Settings page shows the Floor toggle and an Equipment chip only for a group in it), `defaultSettings` (Mon–Fri 09:00–18:00, 45 min, 10-min Snooze, 1 Exercise per Suggestion, Weighted, Intermediate ceiling, no Energetic, no Floor, no Equipment, nothing Excluded, Appearance System) and `initialState`. The Settings page's allowed values, which `ChangeSettings` validates against (`core/settingsChange.ts`): `INTERVALS` (15–120 in steps of 5), `SNOOZE_DELAYS`, `BODY_AREA_MODES` and `APPEARANCE_SETTINGS`, and `WEEKDAYS` (Mon–Sun, the page's order); the enum lists are built with `allOf<T>()`, so one missing a member of its type, or holding one not in it, is a type error. `SettingsChange` (`core/types.ts`) is the `ChangeSettings` event's `change`, used by the validator and the handler's `changeSettings`. `addDays(date, n)` (`core/localTime.ts`) is the calendar date `n` days on.

**Pause and Day Off in the chain** (`chainTimes`, `schedule.ts`).
- A Day Off has no Reminders.
- No Reminder fires inside a Pause `[from, until)`. Walking each day's grid, a Pause that overlaps the gap before the next time (after the anchor or the previous time, up to and including the next one) moves the anchor to its `until`: the first Reminder after a Pause is `until` + Interval, not the old grid, and nothing more that day if that is at or past the window end. Resume early is the same rule with the shortened `until`.
- The chain built when the Pause starts already holds the times after it, since no JavaScript runs when a Pause ends; a Rearm after the end gives the same times. `restOfToday` ends at midnight, so the next day starts as usual (window start + Interval).

**Suggestion rules** (`suggest.ts` and `swap.ts`, tested through `reduce`; all randomness from the injected `Random`).
- Eligible pool: Difficulty at or below the ceiling (Beginner < Intermediate < Expert), Energetic only when `energetic`, Position Floor only when `floor`, no Equipment or owned Equipment, minus `excluded`.
- Areas first. Weighted picks a Body Area among those with a candidate, at weight 3 if the Reminder's day (Settings' time zone) has no Done Exercise in it and 1 otherwise (coverage is the `done` lists of that day's `done` Reminders), then an Exercise uniformly within it. Random does the same with every area at weight 1. Strict takes the next N areas in `BODY_AREAS` order that have something in the pool, wrapping, from the `rotation` of the latest earlier Reminder that has one (else 0), and picks within each; it advances on every Suggestion, whatever the Response. Within a Suggestion each Exercise is from a different area while it can, and never twice.
- No-repeat window: the Exercises of the last 5 Suggestions, swapped-out ones included.
- Relaxation, in order: repeated areas (as many distinct as possible); the window shrinks one step at a time from 5 to 1, keeping the largest that gives the full count; fewer Exercises; in Strict, when its areas have nothing left even at window 1, the rest of the pool drawn as Random would (the rotation still advances); window 0 only when the whole pool was in the previous Suggestion.
- Fallback, only when the pool is empty: the base set (no Equipment, Position not Floor), ignoring Exclusions, the ceiling and Energetic, through the same rules with a count of 1 (the window, the mode and, in Strict, the rotation); the Reminder carries `fallback: true`.
- Swap's replacement, under the current settings, from the pool (the base set for a fallback Reminder): not in the window before this Reminder, this Suggestion or its `swappedOut`. Preference: the same Body Area, then an area not elsewhere in the Suggestion, then any; areas first at weight 1 within that. With nothing left the window shrinks step by step to 0, then swapped-out Exercises come back; never one already in the Suggestion.

**Days, Daily Goal and Streak** (`days.ts`, derived, never stored). A Reminder belongs to the local date (Settings' time zone) of its `firesAt`, its first fire; a Snooze re-fire doesn't move it.
- `dailyGoalFor(state, date)`: the last `goalChanges` entry with `from` on or before `date`, else `DEFAULT_DAILY_GOAL` (4).
- `isGoalDay(state, date)`: the day's `done` Reminders reach that day's goal.
- `dayTally(state, date)` / `todayTally(state, now)`: `{ done, skipped, missed, exercises }`, `exercises` being the total length of the day's `done` lists. Dropped and still-`scheduled` Reminders aren't counted.
- `streak(state, now)`: consecutive Goal Days backwards. Today counts if it is already a Goal Day; otherwise the count starts from yesterday, so an unfinished today doesn't break it. Days Off and days without Active Hours (by the current Settings' weekdays) are skipped, even one that reached its goal. A Pause gets nothing special: a paused day is judged as usual. The first earlier day with Active Hours that isn't a Goal Day ends it; it looks back no further than the earliest Reminder's day.
- `weekMarks(state, now)`: Mon–Fri of the current week (Monday to Sunday, so on a weekend the whole past Mon–Fri), one `DayMark` per day, by precedence `today` (even if already a Goal Day or a Day Off), `dayOff`, `future`, `off` (no Active Hours), `goal`, else `missed`.
- `isDayOff(state, date)`: whether `date` is a Day Off (in `daysOff`).

**Pause and Day Off on Today** (`pause.ts`, tested).
- `heroStatus(state, now, notifications?)`: `{ kind: 'off' }` (Reminders are off: notifications blocked), `{ kind: 'dayOff' }`, `{ kind: 'paused', until }`, `{ kind: 'next', at, snoozed }` (`at` is the re-fire time when `snoozed`) or `{ kind: 'none' }`. When states overlap: `off` > `dayOff` > `paused` > `next` > `none`; a Pause not started yet isn't `paused`. `notifications` is a `NotificationsState`, `'allowed'` or `'blocked'`; absent means `'allowed'`. It is a device fact the adapters read, never stored in `CoreState`; nothing else in the core reads it, so scheduling (the chain, Rearm) is the same either way.
- `canPause(state, now, status = heroStatus(state, now))`: whether a Pause would do something, so the hero offers it (the hero passes the `status` it already has; the default status assumes notifications allowed, so only a passed status can be `off`). False for `off`, `dayOff` and `paused`. Otherwise true whenever a Reminder is outstanding (`outstandingReminder`), which the Pause drops, under `next` or `none`; and under `next` when that next Reminder (its re-fire time when snoozed) falls on today in the Settings' time zone. False under `none` with nothing outstanding, and after the day's last Reminder with nothing outstanding (a Pause would only record a line).
- `todaysPauses(state, now)`: the Pauses whose `from` is today (Settings' time zone), oldest first, for the inline Pause lines.
- `isRunning(pause, now)`: `from <= now < until`, the one rule for a running Pause (`runningPause`, and through it `heroStatus` and the Pause event, and Today's Pause line use it).
- `endsAtMidnight(until, timeZone)`: whether `until` is a local midnight in `timeZone` (`instantAt` of its own date at 00:00), as a Pause for the rest of today ends.

The chain is scheduled ahead because expo-notifications runs no JavaScript when a scheduled notification fires (see #21, "Owner decision: schedule the chain ahead"). Fired Reminders with no Response stay in the shade, bundled in one group, until JS next runs and dismisses the stale ones.

### Tracing (#39)

Temporary logs to diagnose #39 (shade taps answered with a stale Reminder Id, taps delivered minutes late, seconds from tap to commit). They change nothing the app does. Every line starts with `[trace]` and a four-character tag for the JS context (new per context, so the headless task's lines and the UI's stay apart in one process); spans are numbered per context (`#3`).

| Line | Where | Means |
|---|---|---|
| `js start at HH:MM:SS.mmm (ISO)` | `task.ts`, at module load | A JS context started (the app's or a headless task's): line it up with `ActivityManager` `Start proc`, freeze and unfreeze. |
| `bg-task response action=… identifier=… reminderId=… date=… (Ns ago)` | `task.ts`, before `handleAction` | A shade action reached the background task: the notification's `request.identifier`, the Reminder Id parsed from its payload (`ID MISMATCH` if they differ) and when that notification was presented. `Ns ago` large = a late delivery. |
| `fg-listener response …` | `useReminderRuntime.ts`, before `route`/`handleAction` | The same for the foreground response listener. |
| `fg received identifier=… reminderId=… date=…` | `useReminderRuntime.ts` | A notification presented while the app's JS runs. |
| `appState active/background` | `useReminderRuntime.ts` | The app came to the front or left it. |
| `#n <source> <label> \| start at …` then `\| <step> +Xms (Yms) [detail]`, then `\| total Zms: <outcome>` | `handler.ts` `respond` (source `bg-task`, `fg-listener`, `app`), `commitEvent` (Pause, Resume, Day Off, Settings; `app`), `rearmOnOpen` (`app Rearm`) | One handler call: X is the step's own ms, Y since the start. |

The steps, in order: `dismiss` (the tapped notification, `respond` only); `lock` (from the previous step until inside `write()`: the DB open on a cold start, this context's write mutex and `BEGIN IMMEDIATE`'s wait for the other context); `load` (with the Reminder rows loaded); `guard` (`not outstanding`: a stale, duplicate or unknown Id, `respond` only); `reduce` (`unchanged` = the core's no-op); `guarded` (the SQL guard: the kind accepted, or `lost the race`) and `logResponse` (`respond` only); `save` (Reminder rows written); `cancelAll` and `schedule` (`cancelAllScheduledNotificationsAsync`, then how many were scheduled of the chain, how many were ahead of now, the cap, and the first one armed; `no chain` when there was nothing to schedule); `commit`; `dismissNotifications`; `dismissStale` (the outstanding Reminder it kept, as of the call's frozen `now` and how long ago that was, every presented notification `id@time`, and what it dismissed).

### The guided screen

`app/guided/[reminderId].tsx`, opened by Start or a body tap on the notification, or Start on Today. On mount it dismisses the Reminder's notification, then calls `startGuided` once, which cancels a pending Snooze re-fire (`GuidedStarted`) so the re-fire can't arrive mid-flow; on the state it returns, it asks `guidedStart`: the outstanding Reminder opens, and so does one of today's that settled as Missed or dropped, so Start on a Today that hasn't redrawn yet (a newer Reminder fired a moment ago) never dead-ends. It shows the fallback when `guidedStart` refuses it (already answered, another day, unknown), when its Suggestion is empty, or when a Snooze isn't accepted: "This Reminder isn't waiting any more", "It was already answered, or it isn't one of today's. You can change today's answers on Today." and a link back to Today. Otherwise it keeps that Reminder for the whole session, even if it stops being outstanding, and it shows one card per Exercise of the Suggestion: Body Area, Name, the Dose large (`formatDose`), the Cue, the start and end photos (looked up by Id in `exercises`, then `photoSource`; none if missing), "N of M", and **Swap** / **Not this one** / **Did it ✓**. **Swap** calls the handler's `swap` for the card's Exercise: the card then shows the new Exercise (Body Area, Name, Dose, Cue, photos, the timer reset) at the same position and the same "N of M", the cards already answered keep their marks, and a later Did it records the swapped-in Id. A no-op keeps the card and shows "Nothing else fits your settings" under Swap until the next Swap or answer. While a Swap is in flight Swap and the answers are disabled (a ref guards the same tick), so a double tap can't swap twice. A Swap isn't an answer, so the break links stay as they were. A fallback Reminder (`fallback: true`) shows a banner above the card for the whole flow, Swaps included: "No Exercises match your settings" and a **Settings** link that pushes `/settings`. A seconds Dose gets **Start timer**, a countdown that can be restarted (for an each-side Dose, once per side). Until the first card is answered, the break links are **Snooze**, shown only while `isOutstanding` on the latest snapshot says this Reminder is outstanding and `canSnooze` allows it (fewer than 2 Snoozes and no re-fire pending; after the cancel on open, so a once-snoozed Reminder can be snoozed a second time), which goes through `respond(…, 'app')` and then back to Today, or shows the fallback if it turns out a no-op (the Reminder ended meanwhile); and **Skip**, always, which calls `finishGuided` with no Ids and goes back to Today: on the outstanding Reminder that is a Skip, on a Missed or dropped one a correction to Skip. From the second card on, **End here** takes their place. The last card's answer and End here both call `finishGuided` with the Ids marked Did it so far and then go back to Today, recorded or not (what records nothing has nothing new to record): on the outstanding Reminder that is the Done (the core turns an empty list into a Skip); if a newer Reminder fired or it was answered from the shade meanwhile, a finish with a Did it is saved as a correction (see `guidedFinish`), so it isn't lost. Back (the ‹ Today link, Android back or the back gesture, through `usePreventRemove`) before any card is answered records nothing and doesn't bring a cancelled re-fire back: the Reminder stays outstanding until the next Reminder replaces it. Once a card is answered, back saves exactly like End here (`finishGuided` with the Ids marked Did it so far) and then goes to Today; a ref tracks the finish, so back during a finish doesn't finish twice and the finish's own navigation to Today is let through. No celebration until #28.

- **App**: Notifications On or Off (`useNotificationsOn`: On while `'allowed'`, so also before the first read; rechecked when the app comes to the front), with **Turn on** while Off, which opens the app's system settings; Appearance System / Light / Dark (applied by `useAppearance`); **Reset settings to defaults**, behind a confirm (Cancel / Reset) that says the Activity Log is kept, then `resetSettings`; the version (`expoConfig.version`, plus the variant in the development build).

Pickers are JS only: a sheet on React Native's `Modal` with a list of radio `Option`s (`PickerSheet.tsx`, `WindowSheet.tsx`, on `Sheet.tsx`), chips or switches; no native picker. Every change goes through the handler (`changeSettings`, `setDailyGoal`, `resetSettings`); the page shows only what is stored, so a change the core rejects leaves the row as it was. One change at a time: the controls are disabled while one is in flight, and a ref drops a second tap in the same tick. Every colour comes from the theme tokens.

### Onboarding

`app/onboarding.tsx` (#31), on a fresh install only: Today redirects here while the store's onboarding flag is not done (see `store.ts` above; an install with stored settings counts as done and never sees it). One route with three steps, step dots, Back and Next:

1. **Your day**: Active Hours and Interval (`ScheduleRows`).
2. **What do you have nearby?**: Energetic, Floor and Equipment (`WhatICanDoRows` without the Difficulty ceiling).
3. **Permissions**: why notifications matter, **Allow notifications** (`requestNotifications()`, then finish whatever the answer) and **Not now** (finish without asking). Declining still finishes setup.

The first two are pre-filled from the stored state (the defaults on a fresh install) and send each change through the handler's `changeSettings` at once, as Settings does, one at a time. Finishing calls `finishOnboarding()` and `router.replace('/')`, so it runs once. Android back goes to the previous step; on the first step it leaves the app (nothing is under onboarding, as Today's redirect replaced itself). The exact-alarm grant prompt's slot sits in the finish step both Allow notifications (after the request) and Not now pass through: a block behind `exactAlarmGrantNeeded()`, empty for now. If the stored state can't be read (`useCoreState`'s `failed`, with no state), onboarding shows "Setup can't start", a short message and **Go to Today**, which finishes the same way (marks onboarding done, replaces it with Today); the defaults stay for Settings to change.

### Exact alarms: the one switch

`EXACT_ALARM_PERMISSION` in `app.config.ts` is the only place the exact-alarm permission is chosen; `android.permissions` is built from it. It is `USE_EXACT_ALARM` (granted at install; fine for a sideloaded app). For a Play Store release, switch it to `SCHEDULE_EXACT_ALARM` and add a grant prompt: its slot is onboarding's Permissions step, behind `exactAlarmGrantNeeded()` (`notificationPermission.ts`). It reads the built config's `android.permissions` at runtime from `expo-constants` (`Constants.expoConfig?.android?.permissions`, the strings as `app.config.ts` lists them, today `['USE_EXACT_ALARM']`), not `app.config.ts` itself, which stays out of the app bundle; `exactAlarmGrantNeededFor` (`exactAlarm.ts`) decides, so it is false while the list has `USE_EXACT_ALARM`. With either permission, expo-notifications 58 arms `DATE` triggers with `setExactAndAllowWhileIdle` (Doze-safe); it re-arms them after a reboot itself.

**Permission re-grant needs no re-arm today.** `USE_EXACT_ALARM` is granted at install and can't be revoked, and scheduling never reads the notification permission (#31: Reminders stay scheduled while notifications are blocked, see Today's Notifications banner), so granting a permission again changes no alarm. If the switch moves to `SCHEDULE_EXACT_ALARM`, the user can revoke and re-grant "Alarms & reminders", and re-arming on that grant must be handled: expo-notifications doesn't listen for the exact-alarm grant broadcast (`ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`).

### Test mode (development build only)

`app/debug/test-mode.tsx`, linked from Today only when `APP_VARIANT` is `development` (`extra.appVariant`, read with `expo-constants`). Settings sets the schedule now, but only within 15–120 min; Test mode stays as a dev-only page for 2-minute Reminders. On: Interval 2 min, Snooze delay 1 min, Active Hours 00:00–24:00 every day and 3 Exercises per Suggestion, then a Rearm, so a Reminder arrives within 2 minutes (a snoozed one is back within 1) through the real core path. Off: only those four fields go back to `defaultSettings`; every other setting (Suggestions, What I can do, Appearance, `excluded`) is kept. With the window all day, Missed at closing and dropped can't be seen in test mode; Missed on replacement can. It also has a 1 / 3 choice of Exercises per Suggestion (`exercisesPerSuggestion`) for walking the guided flow with one card and with three: choosing re-picks the Suggestions of every Reminder ahead (the Rearm rebuilds every Reminder not yet fired), fired ones keep theirs. An **Empty pool (fallback)** switch: on Excludes every library Id (`excluded`) and Rearms, so every Reminder ahead is a fallback (the guided banner, the notification's fallback line); off restores `excluded: []` and Rearms, keeping every other setting. It still writes settings straight into storage (through `rearmOnOpen`'s `prepare`), because `ChangeSettings` rejects its 2-min Interval and 1-min Snooze delay.

## Exercise Library

The Exercise Library is bundled app data, built at dev time from a vendored source plus our curation files. Nothing in it runs in the app except the generated output.

| Path | What lives there |
|---|---|
| `library/source/exercises.json` | free-exercise-db's `dist/exercises.json`, pinned to one commit and never edited. [`SOURCE.md`](library/source/SOURCE.md) records the commit, date, licence and sha256. |
| `library/curation/<group>.yaml` | One file per group (`base`, `floor`, one per Equipment type), keyed by frozen Id. Only Exercises with an entry ship. Format: [`library/curation/README.md`](library/curation/README.md). |
| `library/photos/<id>/{0,1}.jpg` | The start/end photos of the curated source Exercises, fetched from the pinned commit. |
| `library/library.json`, `library/photos.ts` | **Generated** by `npm run library:build`: the `Exercise[]` and the static photo index (one `require` per photo, so photos ship with EAS Update). Committed; never edit by hand. |
| `tools/library/` | The build (`build.ts`) and draft (`draft.ts`) as pure functions with fixture tests, and the CLI (`cli.ts`, run with `tsx`). |

```sh
npm run library:build            # validate the curation, write library.json and photos.ts; fails on any curation error
npm run library:draft -- <group> # print the uncurated candidates for a group, with the script-filled fields, as YAML
npm run library:photos           # download missing photos of every curated source Exercise at the pinned commit
```

`tools/library/committed.test.ts` rebuilds the library from the files on disk and fails if the committed `library.json` or `photos.ts` is stale, so after changing curation run `npm run library:photos` and `npm run library:build` and commit everything together. It also checks the source file against `SOURCE.md`.

## Lint rules

Two rules guard the architecture, both run by `npm run lint`:

- `core/**` may not import `react`, `react-native`, `expo`, `expo-*` or `@expo/*` (`no-restricted-imports`), and that also covers `require()` and dynamic `import()` (`no-restricted-syntax`).
- Code outside `theme/` may not contain literal colours: hex, `rgb()`/`rgba()`/`hsl()`/`hsla()`, or any string or numeric value given to a `…color` style key or prop (`local/no-literal-colors`, in [`tools/eslint/no-literal-colors.js`](tools/eslint/no-literal-colors.js)). Use `useColors()` from `theme/`. `app.config.ts` is also exempt: it is native config, and the adaptive-icon background is a literal.

Identifiers use US "color" (`useColors`, `backgroundColor`, `no-literal-colors`), following React Native and ESLint convention; prose uses "colour".

## App variants and EAS builds

`app.config.ts` picks the app from `APP_VARIANT`; each [`eas.json`](eas.json) profile sets it.

| EAS profile | `APP_VARIANT` | App name | Android package | Build |
|---|---|---|---|---|
| `preview` | `preview` (also the default when unset) | Activity Reminder | `com.agmarco.activityreminder` | standalone APK, internal distribution |
| `development` | `development` | Activity Reminder (dev) | `com.agmarco.activityreminder.dev` | dev client APK, internal distribution |

The dev app's launcher icon has a plain amber background (the daily app keeps the light-blue grid), so the two are easy to tell apart. Each variant has its own package, so each has its own database.

The two packages differ, so both apps install side by side. Both set `android.allowBackup: true` and `runtimeVersion: { policy: "fingerprint" }`. Check a variant's resolved config with `APP_VARIANT=development npx expo config --type public`.

[`fingerprint.config.js`](fingerprint.config.js) keeps the default (balanced) fingerprint but skips every `package.json` script, so adding or editing a script doesn't change the runtime fingerprint or need a new EAS build.

The app is linked to the EAS project `@agmarco/activity-reminder`: `app.config.ts` sets `owner` and `extra.eas.projectId` (the owner ran `eas init`; a dynamic config can't be written by EAS, so the ID lives there). EAS commands run from `src/`, like everything else. Builds are **owner steps**: `eas build --profile development --platform android` and `eas build --profile preview --platform android` need the Expo account and are run by the owner, not by agents.

### EAS Update and when to rebuild

The `preview` app gets JavaScript and asset changes over the air with EAS Update; the dev app never does (it loads JS from the dev server).

- **Config.** `expo-updates` is installed and **configured, not imported**: no app code imports it, so the current dev build, which doesn't have its native module, keeps running from the dev server. `app.config.ts` sets `updates` per variant: for `preview`, `enabled: true`, `url: https://u.expo.dev/<extra.eas.projectId>`, `checkAutomatically: 'ON_LOAD'` and `fallbackToCacheTimeout: 0`; for `development`, `enabled: false`. The `expo-updates` config plugin writes these to the Android manifest (`expo.modules.updates.ENABLED`, `EXPO_UPDATE_URL`, `EXPO_UPDATES_CHECK_ON_LAUNCH` `ALWAYS`, `EXPO_UPDATES_LAUNCH_WAIT_MS` `0`, `EXPO_RUNTIME_VERSION`).
- **Channel.** The `preview` profile in `eas.json` sets `"channel": "preview"`, so the `preview` build asks for updates on that channel. The `development` profile has no channel.
- **Check on launch, apply on next launch.** At each launch the app starts with the JS it has (the APK's, or the last update it downloaded) and checks the channel in the background without waiting (timeout 0). A new update is downloaded then and runs from the **next** launch (close the app from Recents and open it again).
- **Runtime guard.** `runtimeVersion: { policy: 'fingerprint' }`: the runtime version is a hash of the native project (native modules and their versions, config plugins and the native fields of `app.config.ts`, with `fingerprint.config.js`'s skips). A build only takes updates with its own runtime version, so an update published from JS that needs different native code is ignored by the old build.
- **Publish (owner step, from `src/`):** `APP_VARIANT=preview npx eas-cli@latest update --channel preview --environment preview --message "<what changed>"`. `--environment preview` is required: without it, a non-interactive `eas update` stops with "The `--environment` flag must be set". Like builds, this needs the Expo account and is never run by agents.

**Rebuild or update?**

| Change | Ships with |
|---|---|
| JS or TypeScript under `app/`, `screens/`, `core/`, `platform/`, `theme/`; the Exercise Library output; images and other assets | **EAS Update** |
| Adding, removing or upgrading a package with native code (an `expo-*` module, `react-native`), an `expo` SDK upgrade | **New EAS build** |
| A config plugin, built-in or local (`plugins/`, e.g. the launcher shortcuts), or its options | **New EAS build** |
| Android permissions (e.g. `EXACT_ALARM_PERMISSION`), and other native `app.config.ts` fields: `android.*`, `scheme`, `name`, icons, `userInterfaceStyle`, `updates` | **New EAS build** |
| A build profile's `channel` or `env` in `eas.json` (e.g. `APP_VARIANT`) | **New EAS build**: they are baked into the build when it is made, and the fingerprint doesn't see them |
| `package.json` scripts, docs, tests, other `eas.json` edits (e.g. a new profile) | Neither (not in the app; skipped by the fingerprint) |

**How to tell:** the fingerprint. From `src/`, `APP_VARIANT=preview npx expo-updates fingerprint:generate --platform android` prints the current native project's fingerprint as JSON (its `hash` is the runtime version). If it equals the installed build's runtime version (on its EAS build page, or `npx eas-cli@latest update:list --branch preview`), an EAS Update reaches the phone; if it differs, the change needs a new EAS build, and an update published now would be ignored by the installed app. `npx eas-cli@latest fingerprint:compare` (Expo account) compares against a build directly.

The phone checks for this build (re-arm after reboot and after installing over the old build, Doze, shade taps, EAS Update, light/dark, the launcher shortcuts) are in [`../docs/device-checklist.md`](../docs/device-checklist.md).

### Launcher shortcuts

Long-press the app icon for three static Android shortcuts: **Pause 1 h**, **Pause 2 h** and **Pause today** (long labels "Pause for 1 hour", "Pause for 2 hours", "Pause for the rest of today"). Tapping one opens Today, paused.

- **The config plugin** ([`plugins/withPauseShortcuts.ts`](plugins/withPauseShortcuts.ts)), added to `plugins` in `app.config.ts` with the variant's `scheme` and `package`, writes `res/xml/shortcuts.xml` (`pauseShortcutsXml`): the shortcuts `pause_hour`, `pause_two_hours` and `pause_rest_of_today`, each with the app icon (`@mipmap/ic_launcher`) and one `android.intent.action.VIEW` intent whose `android:data` is `<scheme>://pause/<length>` and whose `android:targetPackage` / `android:targetClass` are the variant's package and its `MainActivity`. It adds the six labels to `res/values/strings.xml` (`addPauseShortcutStrings`, named `<shortcut id>_short` / `_long`) and an `android.app.shortcuts` meta-data pointing at `@xml/shortcuts` to the launcher `MainActivity` (`addShortcutsMetaData`, added once). So the preview app's shortcuts open `activityreminder://pause/…` in `com.agmarco.activityreminder`, the dev app's `activityreminder-dev://pause/…` in `com.agmarco.activityreminder.dev`. It is a native change: the shortcuts reach the phone with the next EAS build. Check the output with a local `APP_VARIANT=development npx expo prebuild --platform android --no-install --clean` (no Expo account needed; `android/` is gitignored, delete it after, and revert the `android` script prebuild rewrites in `package.json`).
- **The deep link** (`app/pause/[length].tsx`): a valid length (`pauseLengthOf`) calls the handler's `pause` once per opening (a ref guards re-renders and a second effect run), then `router.dismissTo('/')` goes to Today: back to it when it is under the link, in the link's place on a cold start. Today shows "Paused until…" through its usual path. A Pause the core rejects (on a Day Off) is a no-op, and an unknown length only goes to Today. The scheme already exists in both variants, so the links work on an installed build without the shortcuts, e.g. `adb shell am start -f 0x1000c000 -a android.intent.action.VIEW -d "activityreminder-dev://pause/hour" -n com.agmarco.activityreminder.dev/.MainActivity`. The flags are the shortcuts' own (`NEW_TASK | CLEAR_TASK | TASK_ON_HOME`, see `adb shell dumpsys shortcut`): without them, a task left in Recents swallows the link (`am start` only brings the old task to the front).
